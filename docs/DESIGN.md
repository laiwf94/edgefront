# edgefront design notes

The first two sections cover the workspace and the steer port. The rest are cachet's design notes, which still describe the cache.

## The workspace

edgefront is one Cargo workspace. Every crate lives under `crates/` and takes its version, edition, lints and dependency pins from the root `Cargo.toml`, and the whole workspace shares one `Cargo.lock`. `crates/edgefront` is the binary. `edgefront-core` holds what every product needs: the HTTP/1.1 listener with steer's connection limits and graceful drain, the pooled client, steer's config schema, metrics and admin plumbing. `edgefront-proxy` is steer's routing and request path, `edgefront-cache` is cachet's engine, `edgefront-limiter` is pacer's rate limiting algorithms, and `edgefront-difftest` diffs the ports against the legacy programs. The root package is cachet as it was before the split, kept until its sources have all moved into the member crates. `legacy/steer` (Go) and `legacy/pacer` (C) kept building and testing in CI, with their full history, until their ports passed their differential suites. Both are now deleted, and their history stays reachable through their import merges.

### Crate map

Each crate and the workspace crates it depends on. There are no cycles: `edgefront-cache` reaches its node through the `cluster::PurgeHost` trait rather than depending on cachet, and `edgefront-limiter` depends on no workspace crate and on serde alone, for its config.

| Crate | Holds | Workspace dependencies |
|---|---|---|
| `crates/edgefront` | The binary: cachet's command line (`--config`, `--check-config`, `--version`, the `CACHET_*` variables, exit codes and JSON log) and `edgefront proxy` | cachet, edgefront-core, edgefront-proxy |
| `.` (`cachet`) | The node runtime still to move: the cache's request path (`proxy`), origins and health checks (`origin`), node start-up (`node`), metric families and the admin routes; and the reference `cachet` binary | edgefront-cache, edgefront-core |
| `crates/edgefront-cache` | Caching policy, Cache-Control and range parsing, objects, request collapsing, purge, cluster gossip, the memory and disk stores, and the cache's config sections | edgefront-core |
| `crates/edgefront-core` | The HTTP/1.1 listener the proxy and the cache both serve on, the pooled client, the clock, request ids, config loading and steer's schema, metrics writers, the admin router and steer's admin API | none |
| `crates/edgefront-proxy` | Routing, path cleaning, forwarding headers, request ids, the balancers and endpoint state, the request path ported from steer, and service discovery | edgefront-core |
| `crates/edgefront-limiter` | pacer's GCRA, keyed table and sliding window, and pacerd's config | none |
| `crates/edgefront-difftest` | Differential drivers against `legacy/steer`, pacer's recorded answers and cachet 0.1 | edgefront-core, edgefront-proxy, edgefront-limiter |

Two tests hold the edgefront binary to cachet's behaviour while both exist. `crates/edgefront/tests/golden.rs` compares the command line's transcripts (usage, config checks, a served request, a purge, shutdown and start failure, log lines included) with `tests/golden/`. `crates/edgefront/tests/e2e_workspace.rs` runs `examples/demo.sh`'s five steps against two edgefront nodes and an origin served by the test, and compares every response's status, `Cache-Status` and body with `tests/fixtures/e2e_workspace.txt` byte for byte. The origin sends no `Date` header and makes objects stale on arrival with `Age`, so no value in the transcript depends on timing and nothing is blanked. The root package's `tests/golden_cli.rs` and `tests/e2e_workspace.rs` run the reference cachet binary against the same files, and CI runs the demo script against both binaries.

## Porting steer: the request path and the differential tests

The port keeps steer's behaviour exactly, byte for byte where bytes are visible, so every decision can be diffed against the Go code before the Go code goes. That means porting the parts of Go's standard library steer leaned on, not only steer's own code. The config reader follows `encoding/json`'s rules (case-insensitive keys, duplicate keys merging, invalid UTF-8 becoming U+FFFD). Durations, addresses, `strconv.Quote` and `path.Clean` follow Go. Request targets are decoded and re-encoded with `net/url`'s rules, and Go's server checks (`Host` validity, `OPTIONS *`, `CONNECT`) come first.

The HTTP/1.1 request path is `edgefront_proxy::server::Proxy`, a handler for the core listener:

1. Go's server checks.
2. Route on the host and the cleaned path.
3. Take a place under the cluster's `max_requests`.
4. Remove hop-by-hop headers and the headers `Connection` names, rewrite the forwarding headers, and set the request ID.
5. Pick the endpoint with the cluster's balancer (below). No pick is `503 no_healthy_upstream`.
6. Send the upstream target: the client's own encoding when cleaning changed nothing, Go's encoding of the cleaned path otherwise.

The body keeps the client's framing, because Go's transport copied `TransferEncoding`: a chunked body stays chunked even after steer buffered it for replay. The cluster's `timeout` covers the whole exchange, so it answers `504` before the response head and cuts the body after it. The place under `max_requests` is held until the response body is dropped, which is when steer's handler returned.

Three layers check the port:

- **Unit and property tests** use Go's own test vectors and, for the trickier functions, fixtures recorded by running steer's Go code.
- **`edgefront-difftest`** (`make difftest`, in CI on every push) feeds 10,000 generated configs and 100,000 generated requests to `legacy/steer/cmd/diffdrive` and to the Rust crates. It fails on any difference in acceptance, error text, route choice or cleaned path.
- **`edgefront-difftest balancer`** (`make difftest-balancer`, in CI on every push) sends 1,000 seeded scenarios to diffdrive's `picks` query and to `edgefront_proxy::balancer::Balancer`. Each scenario has a policy, a panic threshold, endpoints over up to eight priority levels and 10,000 requests, mixed with health flips, ejections, clock moves, in-flight changes and latency samples. Both sides use SplitMix64 from the scenario's seed and a manual clock, and answer one line per operation: the picks of each request, retries included, and the priority state. The first differing line is reported with the scenario's seed, the step, the eight operations before it and a replay command.
- **`edgefront-difftest resilience`** (`make difftest-resilience`, in CI on every push) diffs outlier detection and retry decisions on 5,000 seeded traces of each kind, through diffdrive's `outlier` and `retry` queries. An outlier trace drives one cluster of up to 120 endpoints, each with a failure profile that changes between phases, under a detector configuration drawn from the ranges validation allows. It has 2,000 operations: attempt reports, interval ticks, clock moves long enough for ejections to end and multipliers to decay, cleared ejections and state reads. steer's `outlier.Detector` and `edgefront_proxy::outlier::Detector` must report the same ejections, with the same endpoint, reason and end, and the same multiplier and ejection end for every endpoint at each state read. A retry trace is 1,000 requests, and every hundredth (seed a multiple of 100) is 100,000. Traffic comes in phases of request rate (one to 50,000 a second) and failure rate (none to all), so the budget fills, runs dry and refills as its window slides. Methods, idempotency keys, unreplayable bodies and every attempt outcome are mixed in. On steer's side the decisions come from `proxy.Idempotent`, `proxy.Retryable` and `proxy.GatewayFailure`. These were pulled out of `RoundTrip` in `internal/proxy/decide.go` so the driver calls the code steer runs, not a copy of it. They are joined by `retry.Budget` on a fake clock and `retry.Backoff` with SplitMix64 jitter. Each attempt's class, whether it was retried, refused by the budget or left without an endpoint, the backoff to the nanosecond and the budget's balance must match. The Rust side also keeps its own ledger of requests and retries by second, and fails the run if the budget grants a retry when the window is full or refuses one when it has room. Backoffs are reported but do not move the clock, because `RoundTrip`'s sleep is outside what is diffed. A run takes about 25 seconds.
- **`crates/edgefront/tests/e2e_port_balancer.rs`** sends 20,000 HTTP requests per policy through a proxy built with a manual clock and a seeded generator, to nine origins over three priority levels, while a seeded script walks the cluster through ten phases: spill from level 0 to 1 to 2, panic, ejections that run out, and recovery, with random health flips, latency samples and requests held in flight on top. Each event and request becomes a line of a diffdrive `picks` script. The origins' counts must equal what the responses name, and the per-endpoint counts and a digest of all 60,000 picks must equal a fixture recorded from steer. `make e2e-steer` also runs the script through steer live and reports the first request where the picks differ.
- **`crates/edgefront/tests/e2e_port_http1.rs`** starts the binary with `legacy/steer/examples/steer.json` and three recording fake upstreams. It sends 30 raw requests: the README's traffic, path cleaning, spoofed forwarding headers, request IDs, hop-by-hop headers both ways, body framing, upstream errors and the requests Go refuses. It then compares the response and the upstream's view of each request with a transcript recorded from steer. `make e2e-steer`, also in CI, runs steer live on the same cases and requires it to still produce that transcript.

The HTTP/1.1 transcript only records which priority level answered, so it does not depend on which of the two primaries `least_loaded` picks; `e2e_port_balancer.rs` checks the picks themselves.

### Balancing

Each cluster has one `edgefront_proxy::balancer::Balancer` (steer's `balancer.LB`) over its endpoints, and a pick takes two steps, as in Envoy:

1. **A priority level.** The balancer counts the available endpoints (healthy and not ejected, at the clock's time) per level, up to eight levels. `priority::priority_load` turns those counts into a load per level: each level's health percentage times the overprovisioning factor of 1.4, capped at 100, with what is left spilling to the next level, in integers exactly as steer computes them. If the normalised total health is below the cluster's `panic_threshold_percent`, the pick is in panic and every endpoint, available or not, is a candidate. A roll in `0..100` chooses the level by its load: drawn from the generator, or for Maglev with a key, taken from the key's high half so a key keeps its level. When every endpoint of the chosen level has been tried, the other levels are tried in priority order.
2. **An endpoint in the level**, by the cluster's policy:
   - `round_robin` (`rr.rs`): nginx's smooth weighted round robin. While first attempts keep the same candidate set, one full cycle is recorded and replayed in O(1); any other pick scans. About 27 ns over 100 endpoints.
   - `least_loaded` (`ewma.rs`): power of two choices on `max(latency, 1 µs) × (in flight + 1)`, with steer's peak-EWMA latency estimate. It walks to its two candidates instead of copying the untried ones, so it never allocates. About 115 ns over 100 endpoints, a third of it the one clock read.
   - `maglev` (`maglev.rs`): Maglev consistent hashing on the first value of `hash_header` (steer's FNV-1a and SplitMix64 finaliser of the value), with weighted turns and a cache of the last 8 lookup tables, one per candidate set. A retry walks forward to the next untried owner; a request without the header starts from a random slot. About 40 ns per pick, and a 65,537-slot table over 100 endpoints builds in 2.1 ms.

Endpoint state (`endpoint.rs`, steer's `internal/endpoint`) is what the pick reads, so everything it reads is lock-free: the in-flight count, the health verdict, the end of the current ejection and the latency estimate. The probe and failure runs, interval counters and ejection multiplier change together under one mutex that only health checks, outlier detection and snapshots take. In the request path the endpoint counts the request in flight from the pick until the response body is dropped, and observes the time to the response head on the balancer's clock, at least one second when the attempt failed or answered 5xx so that a failing endpoint never looks fastest. Active health checks (`health.rs`, steer's `internal/health`) drive the verdict: each endpoint is probed at once and then every interval plus a random fraction of the jitter on the injected clock, over a new connection each time, and passes on a 2xx within the timeout; the verdict flips after `unhealthy_threshold` failures or `healthy_threshold` passes in a row, and a probe cut short by shutdown is not recorded. Outlier detection (`outlier.rs`, steer's `internal/outlier`) drives the ejections. Each attempt's outcome is reported to the cluster's detector: `consecutive_gateway_failures` connect errors, resets, timeouts or 502/503/504 in a row eject the endpoint at once. Every `interval` the detector first decays multipliers, then judges the interval that just ended: if at least `success_rate_minimum_hosts` un-ejected endpoints served `success_rate_request_volume` attempts, any whose success rate is below `mean - success_rate_stdev_factor * stdev` is ejected, worst first, unless every rate is equal. An ejection lasts the base time times the endpoint's ejection count, capped at the maximum, and the count drops by one for each full base period the endpoint then stays un-ejected. At most `max_ejection_percent` of the cluster is ejected at once, but always at least one when the percent is above zero, and one mutex serialises the decisions so the cap holds under concurrent reports. An endpoint with no attempts in an interval never counts towards the success rate; steer divides by zero there, but config validation keeps the volume at 1 or more, so the two never differ. `Proxy::endpoints` exposes the same state to tests. Retries (`retry.rs`, steer's `internal/retry` and the retry loop in its `transport.go`) are decided in a fixed order. An attempt may be retried only below `max_retries` and with a replayable body (no body, or one buffered whole because its length is unknown or at most `max_body_bytes`). A connect error is always retriable, since the request never reached the upstream; a timeout, a reset or a `5xx` in `retry_on` only when the request is idempotent (GET, HEAD, OPTIONS, TRACE, PUT, DELETE, or any request with an `Idempotency-Key`). The balancer is then asked for an endpoint not yet tried, and only if it has one is the cluster's budget withdrawn from, so a retry with nowhere to go costs nothing. The budget counts requests and retries in one-second buckets over a window of whole seconds and allows a retry while `retries < min_per_second × window + ratio × requests`, compared in `f64` as steer does; one mutex covers the ring and the clock is read under it, so concurrent withdrawals never overdraw and a stale reading never recycles a newer bucket. The wait before retry `n` is a uniform draw below `min(backoff_max, backoff_base × 2^n)`, with steer's handling of a doubling that overflows, and each attempt is cut off by `per_try_timeout` on the injected clock, the attempt winning a tie.

Every random draw (level rolls, the two choices, keyless Maglev starts) comes from one `rng::Rng`, SplitMix64 in production seeded from entropy, and time comes from `edgefront_core::clock::Clock`. `Proxy::with_sources` takes both, so a test or the difftest can build a proxy whose picks are repeatable and draw in exactly steer's order, which is what lets them be diffed pick for pick.

### Resilience in the request path

`Proxy` runs steer's attempt loop (`RoundTrip` in `transport.go`) inside `Cluster::forward`. A cluster with `retry` deposits every request into its budget and holds each attempt to `per_try_timeout`. Each attempt is classified as an `Outcome`: a response head below 500, a 5xx, a connect error (a connect timeout included), a timeout (per-try, or the client's own) or a reset. It is reported to the cluster's outlier detector, if any, and observed as latency with the failure penalty. Then the policy decides whether it may be retried, the balancer is asked for an endpoint not yet tried, and only then is the budget withdrawn from. The wait is the full-jitter backoff, drawn from the cluster's own SplitMix64. A retried attempt's response has up to 4 KiB of its body read, so a short error body leaves the connection pooled, and is dropped; its endpoint's in-flight count ends there. A body is replayable when it is empty or was buffered whole (`Policy::buffer_limit`); a streaming body goes to the first endpoint only and makes the request unretryable, as in steer. When nothing more may be tried, the last response is delivered, or the last failure answered: `504 upstream_timeout` for a timeout, as steer's error handler mapped `resultTimeout`, and `502 bad_gateway` otherwise. The cluster `timeout` still bounds the whole loop, backoffs included. The access log carries steer's `endpoints` (every endpoint tried, in order) and `attempts`, as well as `endpoint`, the last one.

Health checks and the outlier detector's ticks are background work. `Proxy::run_checks` runs every cluster's `Checker` and `Detector::run` until its shutdown future resolves. `edgefront proxy` spawns it beside the listener and stops it once the listener has drained. The checker and detector share the balancer's endpoint state through `Arc`, so a verdict or an ejection is seen by the next pick with no copying. Without `run_checks`, consecutive gateway failures still eject, since that check runs on every report, but ejections are never judged by success rate and multipliers never decay. `crates/edgefront-proxy/tests/resilience.rs` covers retries on connect errors, listed and unlisted 5xx, unsafe methods with and without `Idempotency-Key`, body replay, oversized bodies, a spent budget, the per-try timeout against a blackholed fake upstream, ejection after consecutive failures, a health check taking an endpoint out and back, and shutdown.

### The admin API

`edgefront_core::admin::Api` is steer's `internal/admin` over a `Control` trait (ready, state, reload, metrics), so it lives in `edgefront-core` without depending on the proxy; the proxy fills in `ProxyState`, `ClusterState`, `BalancerState` and `EndpointState`, which carry steer's `proxy.State` and `endpoint.Snapshot` field for field. It serves steer's five routes: `GET /healthz` and `GET /readyz` are open, so load balancers can probe them, and `GET /metrics`, `GET /clusters` and `POST /reload` need `Authorization: Bearer <token>` when a token is set. A token must be at least 16 bytes; an empty one turns authentication off, which the binary allows only on loopback, as steer did. The token is kept as its SHA-256 digest and a presented token is hashed and compared with no early exit, so neither its length nor a matching prefix shows in the timing. Authentication comes before the method check, so an unauthenticated caller cannot tell which methods a route takes.

The answers are steer's byte for byte, which takes porting what Go's standard library did around steer's code. `admin::go_json` writes JSON as Go's `encoding/json` does: struct fields in declaration order, map keys sorted, `<`, `>`, `&`, U+2028 and U+2029 escaped, floats in Go's shortest form, a nil slice as `null`, times in RFC 3339 with trimmed nanoseconds (in UTC; steer wrote local time, which is UTC in its containers), two-space indentation and a closing newline. A document Go cannot encode, such as a NaN latency, leaves the body empty after a `200`, as Go's encoder failed before writing. Paths are matched as Go 1.27's `ServeMux` matches them: the escaped path is cleaned, a path that cleaning changes gets a `307` to the clean form (with `http.Redirect`'s HTML body for `GET`), and the unescaped result is compared with the routes. A path with a bad `%` escape gets Go's plain `400 Bad Request`, `OPTIONS *` gets an empty `200`, and a `CONNECT` is routed uncleaned and closes its connection. Unknown paths get steer's `not_found` error, whose request ID is always new, because steer wrote it outside its logging wrapper; every other answer keeps a valid inbound `X-Request-Id` (steer's `reqid` rules, now `edgefront_core::reqid`) and carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. Each request on a route is logged as `admin request` with steer's fields.

`legacy/steer/internal/admin/golden_test.go` runs 46 requests through steer's own handler and records each status, header set and body in `crates/edgefront-core/tests/testdata/admin_steer.json`: the open and guarded routes, every way a token can be wrong, refused and accepted reloads, draining, the full, empty and NaN cluster states, unclean and escaped paths, and kept and replaced request IDs. The Go test fails when steer's answers drift from the file, and `crates/edgefront-core/tests/admin_steer.rs` replays every case against `Api` and fails on any difference. What only Go's server does, outside the handler, was checked against a live steer and is covered by unit tests.

### Metrics

`edgefront_core::telemetry::metrics` is steer's `internal/metrics` registry with steer's families on top, so dashboards and alerts written against steer keep working: the names, label names, label values, help text, bucket bounds and the bytes of the exposition are unchanged. A series is a family name plus its labels rendered as Go's `fmt.Sprintf("%q")` rendered them, and `Registry` hands out one shared atomic `Counter` or `Histogram` per series. `SteerMetrics::cluster` creates every per-cluster series when a cluster is built (requests by status class, latency, retries, budget exhaustion, overflow, and attempts per endpoint and result), so the request path holds plain handles and only touches relaxed atomics; the registry's mutex is taken when a configuration is applied, when an ejection reason or health verdict names a series for the first time, and on a scrape. As in steer, series are never removed, so a cluster dropped by a reload keeps its last values, and a reload that keeps a cluster's name and endpoints gets the same series back. The scrape writes counters, then gauges, then histograms, each sorted by series key in byte order, with steer's fourteen bounds from 50 µs to 2.5 s, sums kept in nanoseconds, and floats in Go's `%.6f` with trailing zeros trimmed. The cache's fixed, unlabelled families stay on the simpler writers in `edgefront_core::metrics`.

`legacy/steer/cmd/steer/metrics_golden_test.go` runs the steer binary itself with TLS, two clusters, retries, outlier detection and health checks, drives traffic that makes all 14 families appear (an ejection, both health transitions, a retry, a 5xx, a request with no route, a failed handshake, an applied and a refused reload), and records `/metrics` in `crates/edgefront-core/tests/testdata/metrics_steer.prom` with the upstreams' random ports replaced by fixed ones. `crates/edgefront-core/tests/metrics_steer.rs` replays the same events into `SteerMetrics` and requires the same family set, the same label names per series, and the same exposition line for line, values included, except the histogram buckets and sums that hold the scrape's real latencies.

### Running the proxy: reload, the admin listener and drain

`Proxy` holds its configuration as a `Runtime` (steer's `runtime`): the version, the load time, the router, the clusters and the trusted prefixes, never changed once built. The current one sits in a `tokio::sync::watch` channel. A request takes a reference to the runtime it starts with, one read lock and one reference count, and finishes on it even if a reload lands meanwhile, as steer's requests did. `Proxy::reload` builds the next runtime and swaps it in under a mutex, carrying state over by cluster name as steer's `buildCluster` did. An endpoint that keeps its address keeps its `Arc<State>`: health verdict, ejection and multiplier, failure runs and latency estimate. An endpoint that nothing will probe any more is made healthy, and one that nothing will eject is let back in. The cluster's in-flight counter is shared, so `max_requests` keeps counting requests that started on the old runtime, and a new limit applies to them at once. The client and its connection pool are kept while `connect_timeout` is unchanged, and the retry budget while its settings are. A reload that changes `listen` or `admin_listen` is refused, as in steer. So is any reload of a proxy built `with_filters`, because filters are attached by route index and a new file can renumber its routes. `Proxy::run_checks` subscribes to the channel: after a reload it stops the old runtime's checkers and detectors, waits for them, and starts the new ones.

The request path records steer's series as steer's handler did. A routed request is counted in `steer_requests_total` by the status class the client got, and timed in `steer_request_duration_seconds`, when its response body is dropped. That is when the body has been written or the connection has gone, which matches steer's deferred `finish`. A client that leaves before the head is written is counted as nginx's `499`, as steer counted it. The guard rides in the response body the proxy already has, so a proxied response gains no allocation; a response a filter made gets one wrapper. Each attempt is counted per endpoint and result. A retry is counted once its backoff has passed, a refused withdrawal counts as budget exhaustion, and a refused permit counts as overflow, including a filter's resend or refresh. The outlier and health callbacks count ejections by reason and verdict changes. Reloads count as applied or refused, and a file that fails to load counts as refused through `Proxy::record_failed_reload`. `steer_config_version` reads the version on each scrape. `Proxy::state` fills `ProxyState` from the live runtime, with each ejection's end moved from the monotonic clock to the wall clock at the moment of the call.

`edgefront_core::reload` is steer's `cmd/steer` around this, and `edgefront proxy` is a few lines over it. Settings come from `EDGEFRONT_ADMIN_TOKEN`, `EDGEFRONT_DRAIN_PERIOD` and `EDGEFRONT_SHUTDOWN_TIMEOUT` (`Settings::load` takes the prefix, as `STEER` was steer's), with steer's bounds, and an empty token is accepted only when `admin_listen` is `localhost` or a loopback IP. `reload::load` reads the file and, for a `tls` block, every certificate and key, logging steer's `tls certificate` warnings. `reload::run` serves a `reload::Service`, the trait the proxy implements so that `edgefront-core` does not depend on it: the proxy listener, plain or behind the TLS acceptor with steer's three handshake series registered, and a second `edgefront_core::listener` with steer's admin limits (5 s for the head, 60 s idle, 16 KiB of head) serving `admin::Api` over a `Control` that reads the service. Signals arrive through `reload::Signals`, the process's own (`Signals::os`) or a channel a test drives. SIGHUP and `POST /reload` share one reload path, serialised by a mutex, which re-reads and validates the file, refuses a `tls` block that appears or disappears (the listener would have to change, so it needs a restart, as in steer), loads the new certificates, and applies the file with `Proxy::reload`; the certificates are swapped into the TLS store only once the proxy has taken the rest, so a refused reload changes nothing. On SIGTERM or SIGINT, `Proxy::drain` turns `/readyz` to 503 and adds `Connection: close` to every response. This stands in for Go's `SetKeepAlivesEnabled(false)`: each client finishes its request and reconnects elsewhere. After the drain period both listeners stop accepting and drain with the shutdown timeout, and then the checks stop.

`crates/edgefront-proxy/tests/operate.rs` covers the series over real TCP: attempts, retries and a spent budget, no route, overflow, a client that leaves, ejections and health transitions. It also covers the state against the configuration and the wall clock, and reloads that keep ejections and in-flight counts, keep or replace a budget, let endpoints back in, move health checks and refuse what cannot change, plus draining. `crates/edgefront-proxy/tests/lifecycle.rs` translates steer's `cmd/steer` tests over `reload::run` with the real proxy and upstreams: a SIGHUP reload that switches upstreams, a broken file and a moved listener refused by `POST /reload` and SIGHUP while the old configuration serves and the failures are counted, a good reload by `POST`, the drain (`/readyz` 503 while the proxy still answers, then both listeners closed and the log lines in steer's order), the startup refusals, the shutdown timeout cutting a request in flight, TLS with relative certificate paths, `X-Forwarded-Proto: https`, a certificate rotated by SIGHUP under a live connection that keeps the old one, refused reloads that would turn TLS off or name a missing key, the handshake series on `/metrics`, and a missing or expired certificate at startup. `crates/edgefront/tests/e2e_proxy_admin.rs` drives the binary: every route with and without the token, `/clusters` member for member against the document steer served in the admin golden file, reloads by `POST` and SIGHUP that keep an ejection, a broken file refused twice while the proxy keeps serving, the reload counters, the drain sequence and exit, and the settings refused before anything listens.

### The TLS edge

`edgefront_core::tls` is steer's `internal/tlsedge` on rustls, with ring as the one crypto provider. `Snapshot::load` reads a `tls` block: every certificate chain and key (at most 1 MiB per file, read before it is parsed), each key checked against its leaf by `CertifiedKey::from_der`, and the leaf's validity and subject alternative names read by `tls::der`, a strict DER reader of the few fields the store needs, because rustls verifies certificates but does not expose their fields. The SNI table maps each exact name and each wildcard suffix to its certificates in configuration order, and it is the rustls `ResolvesServerCert` of a `ServerConfig` built per snapshot with the block's minimum version, every TLS 1.3 suite and the listed TLS 1.2 suites, and `http/1.1` as the one ALPN protocol. Selection is steer's: the name lower-cased without one trailing dot, an exact name before a `*.suffix` covering exactly one label, among several certificates for one name the first the client can use (its key signs with a scheme the client offers and, for a client with no TLS 1.3 suite, an offered TLS 1.2 suite authenticates with that key type, which is how an RSA-only client gets the RSA half of an ECDSA and RSA pair), and otherwise the first configured certificate or, under `strict_sni`, no certificate, so the handshake fails. `Snapshot::warnings` reports expired and not-yet-valid certificates and configured names a certificate does not cover, as steer logged them.

`Acceptor` runs the handshakes and `listener::serve_tls` serves HTTP/1.1 behind it. The accept loop takes a handshake slot before it accepts, so once `max_concurrent_handshakes` are running new connections wait in the kernel's backlog instead of in memory, and each handshake runs on its connection's own task under the snapshot's `handshake_timeout`, so a client that connects and stalls holds one slot and nobody else. Each handshake that ends before shutdown is reported as `ok`, `timeout` or `error` with its duration, the labels of steer's `steer_tls_handshakes_total`; handshakes still running at shutdown are dropped and not reported. The header read timeout starts when the handshake is done, as in Go, where the HTTP server's timers start once the TLS listener returns the connection. Each request on a TLS connection carries an `Arc<TlsInfo>` extension with the SNI, the version and the suite.

`tls::Store` publishes the current snapshot, as steer's `Store` did behind its atomic pointer. A handshake reads the store once, when it starts, and finishes on that snapshot's `ServerConfig`, so a swap changes only what later handshakes see: handshakes already running keep the certificates they started with, and established connections never look at the store again, keeping the keys they negotiated. The snapshot sits behind a read-write lock held only to clone or replace the `Arc`, so a reload's file reads happen before it takes the lock and a handshake never waits for them. The handshake cap and timeout are read from the current snapshot too, so a reload that changes them applies to the next handshake.

Two things differ from steer because rustls does not do them. rustls implements no AES-CBC suites, so the four in steer's `compatible` policy are dropped with a warning naming each one, and a `cipher_suites` list of nothing but CBC suites is refused at load. A client whose ALPN list does not include `http/1.1` is refused with `no_application_protocol`, where Go would carry on without ALPN.

`crates/edgefront-core/tests/tls.rs` translates steer's tlsedge tests against the certificates its tests issued, written once by `crates/edgefront-core/tests/fixtures/tls/gen.go` with the same Go code and fixed dates (valid from 2026 to 2126, plus an expired, a not-yet-valid, a nameless and a second CA's certificate): selection, `server_names` overrides, warnings, load errors, and real handshakes for the SNI matrix, the RSA-only client, version and suite policy, strict SNI, the handshake timeout, the handshake cap, shutdown during a handshake and plain HTTP on the TLS port. For the store it checks that a keep-alive connection keeps its certificate across a swap while new connections get the new one, that a handshake already running when the store is swapped finishes on its snapshot, and that 100 reloads from the files, 5 ms apart, under eight clients opening new connections and four sending keep-alive requests, fail no handshake and no request (about 4,000 requests over 1,450 handshakes per run).

### OCSP stapling and session tickets

`tls::ocsp` staples each certificate's OCSP response (RFC 6960, sent as RFC 6066's `status_request`), so clients learn a certificate is not revoked without asking the CA themselves. For a certificate whose chain includes its issuer and whose leaf names an OCSP responder in authorityInfoAccess (or whose listener sets `ocsp_responder`, as nginx's `ssl_stapling_responder`), `Stapler` POSTs an `OCSPRequest` for its `CertID`: SHA-1 of the issuer's name and key with the serial, as RFC 5019's lightweight profile requires, and no nonce. It staples the answer only if the response is `successful` and basic, is signed by the issuer or by a responder certificate it carries that the issuer signed with the OCSP signing key usage (verified with ring: ECDSA P-256 and P-384, RSA PKCS#1 with SHA-256, SHA-384 and SHA-512, and Ed25519), has a `good` status for this `CertID`, and is inside its validity with five minutes of slack. The stapler runs beside the listener and never in a handshake. It refreshes each staple halfway between `thisUpdate` and `nextUpdate` (after an hour when there is no `nextUpdate`). A failed fetch keeps the current staple and retries after a minute, doubling to an hour with up to 10% jitter. A staple past `nextUpdate` is withdrawn rather than served stale. Staples are kept in `Staples`, keyed by the certificate's SHA-256 and shared by every snapshot of the listener, so a reloaded snapshot staples at once, and the stapler wakes on every store swap to fetch for new certificates. A staple is changed by replacing that certificate's `CertifiedKey` whole, so a handshake always sees a staple and its key together. A response is at most 64 KiB, and a fetch at most 10 seconds.

`tls::tickets` gives every snapshot of a listener the same `TicketKeys`, so session resumption survives reloads; rustls's default is a per-configuration session cache, which a reload would empty. Two keys are live: the current one encrypts new tickets and the previous one still decrypts, so a ticket issued just before a rotation resumes after it. Every hour, on the injected clock, the current key becomes the previous one and a fresh key replaces it, so no ticket resumes for more than two hours. The keys are ring's ChaCha20-Poly1305 ticketers from rustls. A key that cannot be made leaves the current one serving and is retried on the next use. TLS 1.2 tickets come from the same keys.

`crates/edgefront-core/tests/ocsp.rs` builds OCSP responses with the fixture CA's key and checks:
- good responses with and without `nextUpdate`, and the slack limits either way;
- revoked, unknown and other-certificate responses;
- a foreign signer, a delegated responder, a same-CA certificate without the signing usage, and a responder from another CA;
- responder statuses other than `successful`, non-basic responses, and garbage.

On a manual clock, a stapler against a fake responder fetches and staples at once (a client reads the staple from the handshake), does not refetch before the halfway point, refreshes after it, staples a reloaded snapshot from the cache, keeps the staple through 503s with retries at one and then two minutes, refuses a revoked answer, and withdraws the staple once it expires. `Stapler::run` fetches for a certificate swapped into the store without waiting. `tests/tls.rs` resumes TLS 1.3 and TLS 1.2 sessions across three hourly rotations, each followed by a reload, and a ticket two rotations old does not resume. `crates/edgefront-proxy/tests/lifecycle.rs` resumes a session across a SIGHUP reload of the running binary.

### Client certificates

`tls::client_auth` turns on mutual TLS for a listener. With `tls.client_auth`, every snapshot's `ServerConfig` gets rustls's WebPKI client verifier over the CA bundle in `client_auth.ca_file` (resolved against the file's directory, like the certificates). A client certificate is accepted only if it chains to one of those CAs, every certificate in the chain is inside its validity, and the leaf allows client authentication. With `required` (the default) a client without a certificate fails the handshake. With `required: false` it is let in without an identity, but a certificate it does present must still be valid. A verified leaf becomes the connection's `ClientIdentity`: its DNS and URI SANs, and its SPIFFE ID, the one URI SAN with the `spiffe` scheme (a certificate with two has none, as the X.509-SVID rules say). Every request on the connection carries it in `TlsInfo::client`.

Routing reads it through a cluster's `allowed_clients`: `spiffe://` IDs, exact or as a `/*` prefix that matches every ID below it (the trust domain compared without case, the path exactly), and `dns:<name>` for a DNS SAN. A request routed to a cluster whose list its client does not match gets `403 client_not_allowed` before anything is sent upstream. A cluster without the list admits every client the handshake let in. Configuration validation refuses `allowed_clients` without `tls.client_auth`. The proxy tells the upstream who called: `X-Client-Spiffe-Id` carries the verified ID, and a value the client sent itself is always removed, so an upstream can trust the header whenever the proxy is its only way in.

`crates/edgefront-core/tests/client_auth.rs` checks the handshake against the fixture client certificates:
- A valid one gets through, and its SAN and SPIFFE ID reach the request.
- An expired one, one from another CA, a server certificate and no certificate at all are refused when certificates are required.
- When they are optional, a client without one gets in with no identity.
- Bad CA bundles and the configuration rules are refused.

`crates/edgefront-proxy/tests/lifecycle.rs` runs the proxy with three restricted clusters and an open one. It checks the 403, the forwarded ID, that a spoofed header never reaches the upstream, the refused handshakes, and the anonymous client under optional verification.

### TLS to upstreams

A cluster's `tls` block makes the proxy speak TLS, or mutual TLS, to its endpoints:
- `ca_file` is the CA bundle the endpoints' certificates must chain to. It is the only set of trust anchors, and the system's are never consulted, so a cluster trusts exactly the CA it names.
- `server_name` is the name the certificates must carry and the SNI sent. By default it is each endpoint's host, which suits name-addressed endpoints. IP-addressed endpoints behind a named certificate need the override.
- `cert_file` and `key_file` are presented as the client certificate.

`edgefront_core::http1::TlsTo` reads the block into a rustls `ClientConfig` (ring, the safe default versions, `http/1.1` as ALPN). `Client::with_tls` sends over it. hyper-util's pooled client cannot take a TLS connector without another dependency, so the TLS client keeps its own pool. It holds idle hyper connections per authority under the same idle timeout and per-origin cap. A connection is offered again once its last response body is read, and a TCP or TLS step past `connect_timeout` is a connect timeout. The client lives in `edgefront-core` with the rest of the TLS stack, so the cache and the limiter can reach TLS origins with the same code, and the proxy's health checks use it too (`Checker::with_tls`), so a probe goes the same way as a request.

A refused handshake is a connect error, which steer's retry rules always retry. A cluster never falls back to cleartext. The block is read on every runtime build, so a reload picks up a rotated CA bundle or client certificate at once. A file that cannot be read fails `reload::load` at startup or reload, naming the cluster. If one disappears between that check and the build, the cluster refuses every attempt (`Client::refusing`) rather than send in cleartext.

`crates/edgefront-proxy/tests/upstream_tls.rs` covers:
- the pinned CA, the name override, and five requests over one pooled connection;
- refusals for no override against an IP, another CA and a wrong name;
- mutual TLS with no certificate, then the client certificate, then a reload that rotates it to another, then an expired one;
- unreadable files that refuse instead of falling back;
- the configuration rules.

`crates/edgefront/tests/e2e_port_failover.rs` runs the resilient failover drill a second time over HTTPS with mutual TLS. The three upstreams terminate TLS for `api.example.com` and require client certificates from the fixture CA, and the cluster's `tls` block pins the CA, names the server and presents the client certificate, for requests and health checks alike. Every phase must keep 100.00%, as over cleartext.

### ACME

`edgefront_core::acme` gets certificates from an ACME CA (RFC 8555) with what the workspace already has: rustls and tokio-rustls for HTTPS to the CA, hyper for HTTP/1.1, ring for the P-256 keys and signatures, serde_json for the messages, and `tls::der` for the CSR.

**The protocol** (`acme::client`).
- `Client::connect` reads the directory over HTTPS, trusting only a given CA bundle (`client::trust`).
- Every later request is a flattened JWS, signed ES256 with the account key: `newAccount` carries the key as a JWK (`Key::jwk`, thumbprint per RFC 7638), and later requests carry the account URL as `kid`.
- Nonces come from the previous answer's `Replay-Nonce`, or from `newNonce`. A `badNonce` problem is retried with its fresh nonce, up to three times.
- Reads are POST-as-GET. Problem documents (RFC 7807) become `AcmeError::Problem`. Each exchange is capped at 1 MiB and 30 s.
- `client::issue` runs a whole order:
  1. `newOrder` for the names;
  2. for each pending authorization, a `Solver` prepares the challenge, the CA is told it is ready, and the authorization is polled until valid (honouring `Retry-After`), with the challenge taken down whatever happened;
  3. the order is polled until ready;
  4. it is finalized with a PKCS#10 CSR for a fresh P-256 key (the first name as the common name, every name as a DNS SAN);
  5. it is polled until valid;
  6. the chain is downloaded.
- `AccountStore` keeps the account key (`account.key`, PKCS#8 PEM) and the account URL per directory (`account.json`) in the state directory, so a restart reuses the account, and the issued `cert.pem` and `key.pem` beside them. The directory is mode 0700, and each file is written at 0600 through a temporary file renamed into place.

**Challenges** (`acme::challenges`, behind the `Solver` trait, each set up before the CA is told and taken down after it decides):
- `Http01` is a handler that answers `/.well-known/acme-challenge/<token>` with the key authorization, and anything else with 404.
- `TlsAlpn01` (RFC 8737) makes a self-signed certificate for the name with a critical `acmeIdentifier` extension holding the SHA-256 of the key authorization, and puts it in `AlpnChallenges`, which every snapshot of a listener shares through `Shared::alpn_challenges`.
  - A listener with `AlpnChallenges` also offers `acme-tls/1`.
  - Its resolver gives a handshake that asks for `acme-tls/1` the challenge certificate for its SNI, or nothing, never a real certificate.
  - The listener closes such a connection right after the handshake, so nothing is served on it.
  - The certificate is built with `CertifiedKey::new`, because rustls's key check would refuse the critical extension that is its point.
  - On such a listener a required client certificate is checked just after the handshake instead of in it, so the CA's validation (which has none) completes while every other client without one is still turned away.
- `Dns01` runs a hook command as `<command…> set <fqdn> <value>` before the challenge and `clear` after, with the base64url SHA-256 of the key authorization at `_acme-challenge.<name>`. It must exit 0 within a minute. It is the challenge that validates `*.` names.

**Renewal** (`acme::renew`).
- `Renewer` issues at once when there is no certificate, then at two thirds of each certificate's lifetime, which for a 90-day certificate is 30 days before it expires.
- A failed attempt is retried after 5 minutes, doubling to 6 hours, each with up to 10% jitter. Near expiry a retry is pulled to an hour before the end at the latest.
- Time comes from an injected `Clock` and the `Wall` time that moves with it.
- Its `Status` holds the validity, the success and failure counts and the last error. `/metrics` exposes it as `edgefront_acme_certificate_expiry_seconds` and `edgefront_acme_renewals_total{result}`.

**In the proxy** (`acme::managed`, `reload::run`).
- A `tls.acme` block names the `directory`, `contact`, `domains`, `challenge` (`http-01` by default, `tls-alpn-01` or `dns-01`) and `state_dir`. Optional are `ca_file` (the directory's trust, by default the first system bundle found), `http_listen` (required for HTTP-01) and `dns_hook` (required for DNS-01). With it, `certificates` may be empty. Validation refuses wildcards on anything but DNS-01.
- The managed certificate on disk joins the configured ones: last, so a configured certificate stays the fallback, or first when there is none. A listener waiting for its first certificate refuses every ordinary handshake.
- `reload::run` binds `http_listen` for HTTP-01 with the other listeners, and offers `acme-tls/1` only for TLS-ALPN-01.
- `AcmeIssuer` orders the certificate. It saves the account URL and the certificate, rebuilds the snapshot from the configuration in force, and swaps it into the store, so new handshakes get the new certificate and open connections keep theirs.
- A reload may change anything but the `acme` block, which needs a restart.

`crates/edgefront-core/tests/acme.rs` runs Pebble, Let's Encrypt's test CA, in Docker, and never a real CA. `tests/common/pebble.rs` starts pinned `pebble` and `pebble-challtestsrv` images on a private network. challtestsrv answers every name with the host's address as containers see it, so Pebble validates against listeners the test opens. Pebble runs with no validation sleep and no random `badNonce`. The tests check:
- an HTTP-01 order for two names, verified by a TLS client that trusts only Pebble's root;
- a TLS-ALPN-01 order through the TLS listener, with the challenge certificate removed afterwards;
- a DNS-01 order for a name and its wildcard, through a hook that sets TXT records in challtestsrv;
- a second client finding the same account through the state directory, and a new key making a new account;
- a failed challenge, a refused name and an untrusted directory, each reported with what failed;
- on a `ManualClock`, 180 days of renewals: issued at day 0 and renewed at days 60, 120 and 180, never within 29 days of expiry, with the metrics checked;
- a CA down at renewal time, retried after about 5, 10 and 20 minutes before it recovers;
- the configuration rules.

The tests need Docker. `crates/edgefront/tests/e2e_acme_mtls.rs` runs the whole path against the binary. The proxy starts with no certificate, gets one from Pebble over TLS-ALPN-01 on its own listener, and requires client certificates (checked after the handshake, so Pebble's validation completes). A client that trusts only Pebble's root and presents the fixture client certificate then reaches an upstream that requires the proxy's own client certificate. The upstream answers with the proxy's SPIFFE ID and the forwarded one of the client. The test also checks the state files at 0600, the refused client without a certificate, and the ACME series on `/metrics`.

### HTTP/2 and gRPC

**The listener.** HTTP/2 shares the HTTP/1.1 listener's accept loop, limits and drain. A connection becomes HTTP/2 by ALPN (`h2`) or, on a cleartext port with `cleartext` set, because its first 24 bytes are the preface. The sniff stops at the first byte that differs, so an HTTP/1.1 request pays one comparison. The watchdog changes meaning for HTTP/2: the header read timeout bounds only the preface, and after it, frames on a connection with no open stream (PING, SETTINGS) do not start a header timer, so the idle timeout governs. Shutdown is hyper's graceful shutdown: GOAWAY, then open streams finish. Over TLS, a client that negotiated `h2` and then sends something other than the preface gets SETTINGS, GOAWAY(PROTOCOL_ERROR) and a TLS close, which is what h2spec's 3.5/2 checks. On a shared cleartext port the same bytes are an HTTP/1.1 request and get an HTTP/1.1 400, so `tests/h2.rs` expects 145 of 146 there and 146 of 146 over TLS.

**The upstream pool** (`h2::pool`) is written on h2 directly, not hyper's client, for two reasons. First, why a stream failed decides whether it may be sent again: h2's error says whether the origin excluded it with GOAWAY or refused it, and hyper's does not. Second, the pool owns its windows. Per origin it keeps at most three connections. A request takes the least busy connection under 100 streams; otherwise one new connection is opened, one connect at a time; past the cap it overflows onto the least busy one, where h2 queues it behind the origin's own stream limit. A GOAWAY drains a connection: no new streams, the open ones finish, and the reaper closes it. In cleartext, whether an origin speaks HTTP/2 shows in its first frame (it must be SETTINGS), which a small read tap checks before the first request is sent. This is what lets `protocol = "auto"` downgrade without sending a request twice.

**Flow control** (`h2::flow`). A window W over round trip R carries at most W/R per stream. The pool starts at 1 MiB and samples the bandwidth-delay product with PINGs while data arrives. When a round trip carries two thirds of the window, the window doubles (or becomes twice what was seen), up to 16 MiB. Bytes count as the reader consumes them, so a slow client never grows the windows and the memory a stream can hold stays bounded by what is actually moving. hyper's adaptive window does the same but starts at 64 KiB, and on a 25 MB/s link with 50 ms each way it reached 81.3% of TCP for 100 MB, against 92.6% for the pool's estimator (`tests/h2_flow.rs`, a simulated link: serialisation at the link rate, then the one-way delay, in each direction).

**gRPC** (`edgefront_proxy::grpc`) is plain HTTP/2 to the proxy, plus three rules. `grpc-timeout` shortens the cluster's deadline and is rewritten to the time left. The proxy's own errors become Trailers-Only responses with the HTTP-to-gRPC status mapping. And an HTTP/2 request body without `content-length` streams instead of being read as empty. Trailers need nothing special: response frames, trailers included, pass through the same body wrapper as HTTP/1.1 data. The tests use tonic as a dev-dependency only, with a bytes codec of their own, so no protobuf compiler or generated code enters the build.

**The benchmark** (`crates/edgefront-bench/scenarios/h2_grpc.toml`) puts edgefront proxy, Envoy and HAProxy (`bench/targets/*-h2`) between the load generator and the origin with HTTP/2 on both sides, at 1,000 concurrent streams. An open-loop generator does not choose its concurrency, so the scenario sets it through Little's law: the origin holds every request 200 ms (`origin_delay`), and at 5,000 requests a second about 1,000 streams are open at once, 100 on each of the 10 load connections, and as many upstream. The load generator counts the most requests on the wire at once, and each result reports it as `measured.peak_in_flight`, so a run that did not reach the streams it claims shows it. One scenario sends GETs of 4 KiB objects, the other unary gRPC calls whose one message names a 1 KiB object; a call counts only if it ends HTTP 200 with `grpc-status: 0`, and any other ending is `measured.errors.grpc`. Each product is given the same room: 1,000 streams a connection on each side, and no request limit below the load. edgefront's `max_requests`, a circuit breaker of 1,024 concurrent requests per cluster by default, is raised for it as Envoy's breakers are, since the peak runs a little past 1,000 and the default refused 7 and 29 of 25,000 gRPC calls as `overflow` in two short runs.

### Service discovery

**Sources and the merger** (`edgefront_proxy::discovery`). A source is a task that sends updates down a channel: a whole set, one endpoint added or changed, one removed, or a failure. DNS, SRV and files send whole sets; Kubernetes sends whole sets after each list and watch event; the delta feed sends a snapshot and then single changes. Each cluster has one `Merger`, which keeps each source's set apart and merges them: one entry per address, the first source listed wins an address's weight, priority, zone and readiness, a failure keeps the source's last known good set and marks it stale, a source that never answered contributes nothing, and a successful empty answer empties the source (only failures keep old sets, so a record removed from DNS does stop traffic). A not-ready endpoint stays in the set with `ready: false`, so a readiness flip is a change, not a removal and an add. The merger settles only the addresses an update touches, so merging one change does not grow with the size of the set.

**Applying a change** (`Proxy::run_checks`). Updates are coalesced: each is applied with whatever is already queued behind it, up to 4,096, and then only the clusters whose merged set moved are rebuilt, each once, and swapped into the runtime in force. Routes, other clusters and the configuration version are untouched. Endpoints that stay keep their balancer state, health and attempt series; the series of removed ones are dropped so churn does not grow `/metrics`. The health checker and outlier detector take the new list in place: a staying endpoint keeps its probe schedule and a new one is probed at once.

**DNS without a stale cache.** hickory-resolver is used for its protocol and transport, but its cache is cleared before each lookup, and the next lookup is scheduled from the shortest TTL of the records the set came from (between 500 ms and 5 minutes). So the time an endpoint removed from DNS keeps traffic is bounded by its TTL, plus the lookup and the apply.

**Kubernetes without kube-rs.** kube-rs with k8s-openapi added 5.9 MB to a 14.1 MB release binary for two requests, list and watch, so the watcher is written on the HTTP/1.1 client edgefront already has. It lists in pages, watches from the list's resource version with bookmarks, resumes a cut watch from the last version seen, and lists again on 410 Gone.

**The delta feed** (`discovery::delta`) is NDJSON over one HTTP/2 stream: a `snapshot` or `resume` line, then `upsert` and `remove` lines whose versions rise by exactly one, and heartbeats when quiet. The resume token is `<feed id>.<version>`; the feed id is random per feed, so a restarted control plane that lost its history is never asked to continue it and sends a snapshot instead. The client refuses a skipped or repeated version and starts again from a snapshot, so a set can never silently drift from the feed's.

**End to end** (`crates/edgefront/tests/e2e_discovery.rs`). Four tests start the binary with one cluster fed by DNS A records, SRV records, a watched file or a delta feed in the test process, with four clients sending requests through it the whole time and the upstreams recording when each request reached them. A record added to DNS took traffic about 0.7 s later and a removed one took its last request about 0.7 s after it went, against the 2 s bound for a 1 s TTL. SRV weights of 30 and 10 split the load exactly 3 to 1, and removing the priority-10 records moved everything to the backup. A DNS outage, a broken and then deleted file, and a delta feed killed mid-stream all kept the last endpoints serving with `edgefront_discovery_stale` at 1; the restarted feed was resumed from the proxy's token, one snapshot in all. Once the first answer reached the cluster, every request in every test was answered 200.

**What is not met yet.** The W07 target for the delta feed, a balancer update p99 under 5 ms at 100,000 endpoints taking 1,000 changes a second, is not met: `benches/discovery.rs` measures 31 to 33 ms, because each batch still rebuilds the cluster's endpoint list and balancer in O(n). It holds at 10,000 endpoints (3.8 ms). The Kubernetes source is tested against a fake API server speaking the documented watch protocol, not yet against a kind cluster.

### After steer: deletion, the frozen suite and the benchmark

legacy/steer was deleted (#86) once the differential suite, the `steer-difftest` job of the difftest workflow, had passed on eleven consecutive runs on main: configs and routes, balancers, resilience, and the live end-to-end runs. The deleting commit names those runs. The suite keeps running against steer frozen at its last commit, `STEER_REV` (8f0c2a5) in the Makefile. `make steer-src` extracts that tree from history with `git archive` into `target/steer-src`, the diff targets build the driver and the binary from there, and the workflow checks out the full history so the commit is there. The Go-vs-Rust comparison is [docs/benchmarks/steer-go-vs-rust.md](benchmarks/steer-go-vs-rust.md). ### The failover drill

steer's README publishes one table as the measure of its resilience: its failover drill, in which two priority-0 upstreams and a priority-1 backup take 200 requests per second while one fault lands per 10-second phase (a primary killed with SIGKILL, the other failing half its requests, then that one blackholed), and every phase keeps 100.00% of requests with health checks, outlier detection and retries on. The port is held to the same table. `examples/failover.sh` is steer's script with the proxy swapped, and the configurations in `examples/failover/` are steer's, byte for byte, so the comparison is between the two binaries and nothing else.

The drill's tools are ported too, into `edgefront_difftest::drill`, so the drill outlived legacy/steer's deletion. `Upstream` serves `edgefront_proxy::fakeupstream` on a traffic and a control address, as `cmd/upstream` did, and `edgefront-difftest upstream` runs it as a process the shell drill can kill. `load` is `cmd/loadgen`, kept to its semantics so the numbers mean the same: request `i` is due at `start + i × interval`, with Go's truncated interval, whatever earlier requests did, and its latency runs from that due time, so a stall shows in every request it delays (no coordinated omission); success is a 2xx with its body read; a request still unanswered `timeout` after it was sent is a `timeout`; requests beyond `max_inflight` outstanding are `dropped`; and the percentiles are nearest-rank over every request sent, failures included at the time they failed. This differs from `edgefront_bench::load`, which leaves failures out of its histograms and queues requests behind a fixed set of connections; the drill needs steer's numbers, the benchmark harness needs its own. The client is hyper-util's pooled client, as close as hyper gets to Go's `http.Transport` with `MaxIdleConnsPerHost` at the in-flight limit.

`crates/edgefront/tests/e2e_port_failover.rs` runs the drill in process: the upstreams and the load generator on a tokio runtime in the test, the binary as a child on free ports. `Upstream::kill` stands in for SIGKILL by aborting both listeners and every connection task, so held and in-flight requests end without an answer and new connections are refused, which is what the proxy sees when the process dies. The test with the features on requires every phase at 100.00%, p99 under 100 ms in the first three phases, the slowest request of the blackhole phase under 750 ms (the per-try timeout at work; without it a request waits for the 1 s cluster timeout), and the end state steer's drill prints: both primaries unhealthy, primary-b ejected, the backup taking all the load. The test with them off requires the faults to show as 502s, 503s and 504s at a p99 of at least the cluster timeout, which proves the drill breaks what it claims to. The two run in parallel, each with its own proxy and upstreams, in about 45 seconds. `scripts/check-failover.sh` applies the success-rate half of these checks to either script's transcript, and the `failover-drill` CI job runs it on both.

## Porting pacer: the limiter algorithms

`edgefront-limiter` is libpacer's `gcra.c`, `gcra_math.h`, `siphash.c`, `table.c` and `window.c` in safe Rust, with no dependencies. (The crate's one dependency, serde, serves the config described below.) The port keeps the C's arithmetic and memory layout, not only its behaviour, so that a table holding the same keys holds them in the same slots and evicts the same ones.

- **GCRA.** A limiter's changing state is its theoretical arrival time (TAT), one `AtomicU64` in ticks of 1/64 ns, so high byte rates keep their fractional intervals; the interval and tolerance sit in two more words that only `reconfigure` writes. A decision is a pure function from the TAT, the interval, the tolerance (burst times interval) and the time to a new TAT and a `Decision` (allowed, granted, remaining, retry-after in nanoseconds, rounded up). `Gcra` applies it with a relaxed compare-and-swap loop, and `Table` applies the same function under its shard lock. libpacer clamped times past 2^57 ns, about four and a half years of uptime; `Gcra` and `Table` store the TAT from a moving epoch instead (below). `reconfigure` changes the rate while takes race with it and keeps debt as time: a client that had to wait 2 s still waits 2 s. A take at the same moment may mix the old interval with the new tolerance, and is then bounded by the larger of the two rates.
- **Keyed table.** All memory is allocated in `Table::new`: power-of-two shards picked by the top hash bits, each a 64-byte-aligned mutex over a linear-probing array kept at most three quarters full, 64-byte entries aligned to cache lines and an intrusive LRU list. Deletion shifts the probe chain back instead of leaving tombstones. When a shard is full it first reclaims an idle entry (one whose bucket has refilled and that holds nothing), then denies the new key or evicts the coldest of the eight least recent entries that hold nothing. Keys are hashed with SipHash-1-3 under a random key by default; SipHash-2-4, libpacer's choice, is kept so the differential tests can place keys exactly as the C does.
- **Window.** A fixed 168-byte value owned by one connection: up to 16 buckets plus the bucket being filled, with the oldest bucket weighted by the part of it still inside the window. Times that go backwards count at the newest time seen, and a jump of a whole window clears it.

Two inputs make the C wrong, and the Rust refuses them rather than copying the bug:

- `pacer_rate_ticks` multiplied interval by burst in wrapping 128-bit arithmetic, so a rate such as one token per 2^60 ns with a burst of 2^62 wrapped to a tolerance of 0 and the next take divided by zero. `Rate::ticks` returns `InvalidRate` on any overflow.
- `window.c` tested `now < head_start + slot_ns`, which wraps near the top of the clock. The Rust compares the difference, which agrees whenever the C does not wrap.

The generator keeps clear of both (`wraps_in_c`, and a clock at or below 2^60), and everything else is compared exactly. Four layers check the port:

- **Unit tests** port every case of `test_gcra.c`, `test_table.c`, `test_siphash.c` and `test_window.c`, plus threaded tests that also run under ThreadSanitizer.
- **`tests/model_gcra.rs`** holds `Gcra` to a token bucket kept as an exact reduced rational, through seeded scripts and a proptest tape that shrinks to a minimal failing script. A failure prints the seed and a replay command.
- **libpacer's `tests/diffdrive.c`** (deleted with legacy/pacer in week 4, after its answers were recorded) read one operation per line (clock, `gcra`, `table` and `window` operations) and printed the decision and the full state after it: TAT, interval and tolerance, table stats and invariant checks, window start and total. `edgefront-difftest` answers the same protocol from the Rust crate, byte for byte, and generates scripts that mix four limiters, three tables and three windows under one clock that jumps, goes backwards and passes the clamp. Each script ends by dumping every live object. The first differing line is reported with its seed, its step, the eight steps before it and a replay command.
- **`crates/edgefront-difftest/tests/e2e_limiter_port.rs`** drives the `edgefront-difftest` binary: one million generated operations against libpacer's recorded transcripts on every push (`pacer-recorded`; until week 4, against the C driver live), a divergence that must replay from the command it prints, and a worked example (per-key limits with exact retry times, then an hourly window quota) whose answers are written out in the test.

### The moving epoch

libpacer's TAT was absolute ticks in 64 bits. With up to 2^62 ticks of tolerance on top of the clock, that runs out at 2^57 ns, about 4.57 years of uptime, so pacer clamped every later timestamp and its limiters stopped refilling. `edgefront_limiter::clock` splits time into epochs of 2^56 ns (about 2.28 years, exactly the largest tolerance), and `Gcra` stores its TAT as an offset from an epoch:

- **Two words.** `base`, the limiter's base epoch, only grows. The TAT word's top bit is the parity of the epoch its 63-bit offset counts from, which is always `base` or `base + 1`. An offset holds just under two epochs, so the pair covers three: every arrival time a caller in either epoch can produce, with the full tolerance on top.
- **Lowest epoch first.** A write stores the new TAT from the lowest epoch that holds it and never below the base. Within one epoch the decision runs on 64-bit offsets, as before; across epochs it runs on 128-bit absolute ticks, then stores the result the same way. Any `u64` timestamp (584 years) is valid.
- **Rebasing.** When an arrival time would need an epoch past `base + 1`, the limiter first moves the TAT word up to `base + 1` (one CAS), then the base behind it (another). Each is a single CAS that another thread can finish just as well, so the limiter stays lock-free. A limiter idle for a century catches up in about 90 such steps, once.
- **Readers** on the slow path load `base`, the TAT word and `base` again, and retry if the base moved, so a word is never decoded against the wrong epoch. The fast path loads the base once: the base cannot move past the timestamp's epoch while every caller is within one epoch of it.
- **Contract.** Callers sharing a limiter must use timestamps within one epoch of each other, which any monotonic clock gives. Only a refund can move the TAT back. A refund dated before the base epoch's start stores that start, not the earlier time.

The fast path, when the TAT word and the timestamp share an epoch, checks one parity bit against a tag computed from the timestamp and runs the same 64-bit step as before. The slow paths are out of line. The cost is one more word per limiter (32 bytes) and one load of the base. Single-thread `gcra take`, alternating the old and new builds three times on the same 4-vCPU machine, gave 154 to 187M decisions per second before and 163 to 165M after, within the run-to-run spread. One trap on the way: closures that captured the rate by reference sent its address into the out-of-line slow path. The compiler then reloaded the interval from memory, lost the fact that it is non-zero, and kept a division the caller never used. That halved throughput to 89M. The closures now capture by value.

**The keyed table** has a lock per shard already, so it does not need the parity word. Each shard keeps a base epoch, and its entries keep their TATs as 64-bit offsets from the start of it. The base is one epoch behind the newest timestamp the shard has seen, or 0. Under the shard lock, the timestamp is turned into an offset first, and one two or more epochs past the base moves the base up to the epoch before it, in one pass over the shard's slots that shifts every entry down. That pass runs at most once every 2.28 years per shard, and an idle century costs one pass, not 44. The timestamp's offset is then below two epochs, so an entry's TAT, with the deepest tolerance on top, stays below 2^64 and the decision runs on the same 64-bit step as before. A TAT that would fall before the new base's start becomes that start: it is more than an epoch older than any timestamp the shard accepts, so the entry was a full bucket and stays one, and no decision changes. `Table::get` reports the TAT as 128-bit ticks since the clock's start. The table's contract is the `Gcra`'s: callers within one epoch of each other, and a timestamp before the base epoch's start counts as that start. The hot path gains one compare and one subtraction under the lock. Alternating the old and new builds twice on the same 4-vCPU machine, `table take` gave 26.3 and 26.8M decisions per second before and 26.5 and 26.1M after with 10k keys, and 53.4 and 54.3M before and 48.6 and 52.7M after with one hot key, within the run-to-run spread.

Under libpacer's horizon the decisions are unchanged: below 2^57 ns no base ever moves (every arrival time fits in epochs 0 and 1, and a table's base moves only at the start of epoch 2), and the difftest interpreter applies libpacer's clamp before calling `Gcra` or `Table`, so the C and Rust still agree line for line. Without the clamp on tables the difftest diverges in its first script. `tests/model_gcra.rs` runs its exact reference model at 4.5, 10 and 100 years of synthetic uptime, from just before an epoch boundary, and with idle gaps of up to three epochs over 24. The table's reference model, a map and a recency queue with 128-bit absolute TATs, does the same in `table.rs`: 12 seeds of 3,000 operations for each uptime, starting there, starting 10 s before an epoch boundary with keys in debt, and with idle jumps of up to three epochs. Putting libpacer's clamp back fails each of the three. `clock::ManualClock` and `clock::MonotonicClock` implement the `Clock` trait that callers read `now_ns` from.

### pacerd's config

`edgefront_limiter::config` is pacerd's `config.c`. `parse_pacerd` takes the file's bytes and gives a typed `LimiterConfig` (workers, admin socket, drain timeout, log level and up to 16 `ListenerConfig`s), or a `ConfigError` with pacerd's line number and message, word for word: `line 12: per_ip_conn_rate: expected a rate like 10/s, 600/m or 1m/s, got "10/d"`. To keep acceptance identical, it reproduces config.c's limits as well as its grammar:

- The file is at most 1 MiB and each line at most 1,024 bytes. A NUL byte is an error. A line has at most eight words, separated by spaces, tabs and carriage returns only, and `#` starts a comment even in the middle of a word.
- A number in a size or duration has at most 23 digits, leading zeros included. Sizes and rate counts are at most 2^50, and durations at most 24 hours before each directive's own range applies.
- Addresses are numeric `a.b.c.d:port` or `[v6]:port`. Leading zeros in an IPv4 octet are refused, as glibc's `inet_pton` refuses them. A port is 1 to 65535 and may have leading zeros.
- A directive may be set once per scope. Top-level directives keep their scope across listener blocks, so `workers` after a block still counts as a repeat.
- Tokens quoted in messages show printable ASCII except `"`, replace every other byte with `?`, and are cut at 44 bytes with `...`.
- Errors found at the end of the file name its last line, and a file over the limit names line 0.

The same directive table serves the serde form, which is how the limiter appears in an edgefront config. Field names are the directive names, and listeners are a `listeners` array with a `name` each. A value is the directive's text as a string (`"10/s burst 20"`, `"512 per 10s"`), or an integer where pacerd takes a bare number or size. Each value goes through the same parser, so a TOML error is the pacerd message with the field's path in place of the line: `listeners[0].max_conns: must be between 1 and 1000000`. The admin socket path is taken whole, so in TOML it may contain spaces.

The serde form also says two things pacerd.conf cannot, both from `rate::RateSpec`:

- **Rates in `RateSpec` syntax.** `per_ip_conn_rate`, `per_ip_bandwidth` and `bandwidth` are first read by pacerd's parser, so every pacerd rate keeps its meaning and its `Rate` value, and the config difftest stays at 0 divergences. Text pacerd refuses is then read as a `RateSpec`, whose refusal is the one reported. The count over the period is kept in lowest terms with the period in whole seconds (`2.5/10s` is 5 per 20 s), not in `RateSpec`'s own lowest terms, which may need a sub-second period (1 per 400 ms) that no text can write back. A rate whose exact period would overflow 64 bits that way is refused as too precise. A quota-shaped rate (a period of an hour or more with no burst) is refused in these fields, which are token buckets.
- **`per_ip_conn_quota`**, a `ConnQuota { limit, window }`: at most `limit` new connections per client in any `window`, from an hour to 366 days, which is `RateSpec`'s quota plan. A rate-shaped value is refused. Its line is recorded in the `SourceMap` like a directive's, and it counts as per-client admission for `table-below-max-conns`, `unused-table` and the IPv6 prefix lints.

Writing back, a rate pacerd can hold is written in pacerd's text, and any other as `RateSpec` text with the burst always written (`1/2s burst 30`, `10/day burst 10`), so it cannot read back as a quota. `to_pacerd` refuses a config with a quota or with such a rate, naming the field. Both writers leave out every value equal to pacerd's default, so `edgefront check --print`, which writes any limiter config as TOML, gives a file that says only what it changes and lints exactly as its source does.

`LimiterConfig::to_pacerd` and `Serialize` write a config back out, choosing the largest unit that is exact (`2m`, `16k`). `validate` checks a config built in code by writing it and reading it back. A value neither syntax can express is an error naming the field: a duration that is not a whole number of milliseconds, a rate period other than a second, minute or hour, or an IPv6 scope id. Property tests round-trip generated configs through both syntaxes.

The reader is fuzzed by `crates/edgefront-limiter/fuzz/fuzz_targets/limiter_config.rs`, which replaces pacer's `fuzz/fuzz_config.c`. It starts from pacer's three corpus files and its dictionary, kept in the crate because `legacy/pacer` went in week 4; the dictionary adds the log levels and a few values pacer's left out, and `tests/fuzz_seeds.rs` fails if it loses a directive name or if a seed stops parsing. Beyond pacer's checks (an accepted file has 1 to 16 listeners, 1 to 64 workers, valid names, buffers of at least 1 KiB, tables of at least 16 keys and rates the limiter takes; an error is one printable line starting `line N:`), each input must also:

- name a line of the file in its error, line 0 only for the empty file or one over 1 MiB, and get the same error from `parse_pacerd` again;
- if accepted, pass `validate`, have no two listeners with the same name, and write out as pacerd.conf and as TOML, each reading back into an equal config;
- lint without a panic, each finding on a line of the file, about one of its listeners, in printable text.

CI runs it for 30 minutes on every push with `-timeout=10`, so a parse that loops or goes quadratic fails like a crash. A local 30-minute run made 20.4 million executions at about 11,300 a second, reached 2,848 coverage edges and a corpus of 781 inputs, and found nothing. Two bugs put in by hand were each found within three minutes: letting control bytes into quoted tokens, and writing sizes of 2 GiB and up one MiB too large.

### Config lints

A config can parse and still not do what it says. `edgefront_limiter::lint` reads a valid `LimiterConfig` and reports what pacerd would actually do with it, and `edgefront check [--allow CLASS]... FILE` prints each finding as `FILE:LINE: warning[CLASS]: listener NAME: MESSAGE`, then a count, exiting 1 when there are findings, 0 with `FILE: ok` when there are none and 2 when the file does not parse. A `.toml` file is the limiter section in the serde form; anything else is a pacerd.conf. The line comes from a `SourceMap`: `parse_pacerd_mapped` records the line of each directive and each `listener NAME {`, and for TOML the binary reads toml's spans for each key and `[[listeners]]` header. A setting left at its default is reported on the line that opens its listener.

Each class is a fact about pacerd's data path, and the unit tests check the facts the messages state against the limiter itself:

| class | reported when | why it matters |
|---|---|---|
| `burst-below-read` | `bandwidth` or `per_ip_bandwidth` has a burst below the smaller of 4 KiB and `buffer` | `reserve` asks a byte limiter for at least that much, and the limiter clamps the minimum to the burst. Reads are cut to the burst, not refused, and a busy connection wakes once per burst (a test drives `take_range` the way `reserve` does) |
| `listen-overlap` | a listener's address and an earlier one share a family and port, and exactly one is a wildcard | pacerd binds every listener with `SO_REUSEPORT`, so both bind and the kernel gives each connection to the most specific socket: the wildcard listener's limits never see that address's clients. IPv6 sockets are `V6ONLY`, so `[::]` and `0.0.0.0` do not overlap |
| `table-below-max-conns` | `per_ip_max_conns` or `per_ip_conn_rate` is set and `table_size` is below `max_conns` | each connected client holds a table entry, and a held entry is never reclaimed or evicted, so client `table_size + 1` is refused as `table_full` under either policy while the listener has room (tested on a `Table` under both policies) |
| `per-ip-cap-unreachable` | `per_ip_max_conns` is at least `max_conns` | one client reaches the listener's own cap first |
| `per-ip-bandwidth-unreachable` | `per_ip_bandwidth` is at least `bandwidth` in rate (compared exactly) and in burst | one client's bytes are a share of the listener's, so the listener limit binds first |
| `rate-rounding` | a rate is enforced more than 1% slower than written | a bucket's interval rounds up to a whole tick of 1/64 ns. pacerd's byte rates are commonly a little over 0.1% slow (`100m/s` by 0.106%), which is noise for a bandwidth cap; at 16 GiB a second it is 6.9%, and above 64 billion a second the exact interval is below one tick, so the rate enforced is 64 billion a second whatever is written |
| `unused-table` | `table_size` or `table_full` is written but no per-client limit is set | the client table is never consulted |
| `ipv6-prefix-unused` | `ipv6_prefix` is written on an IPv4 listener or on one without per-client limits | no client is ever grouped by it |
| `wide-ipv6-prefix` | per-client limits group an IPv6 listener's clients by a prefix shorter than /48 | /48 is one end site, so a shorter prefix makes several sites, or a provider, share one client's limit |
| `upstream-loop` | the upstream is a listener's address, or a loopback or unspecified address on a wildcard listener's port | every connection comes back into pacerd. Another address on a wildcard listener's port may be a different host, so it is not reported |
| `quota-unreachable` | `per_ip_conn_quota`'s limit is at least `per_ip_conn_rate`'s burst plus what the bucket refills in the quota's window, compared exactly | the bucket can never admit that many in one window, and its rounding only makes it slower, so the quota never refuses anyone. TOML only, since pacerd.conf has no quotas |

A config built in code has no source map; its findings carry line 0, and the two classes that depend on what was written out (`unused-table` and `ipv6-prefix-unused`) are skipped. pacer's `examples/pacerd.conf` lints clean, and every config pacer's tests and corpus accept lints without a finding outside the file.

### Rates, units and quotas

pacerd took whole counts per second, minute or hour (`10/s`, `600/m`), so half a request a second or a daily quota could not be written. `edgefront_limiter::rate::RateSpec` reads `COUNT/PERIOD [burst N]`: a count with up to nine decimal places and pacer's `k`, `m` and `g` multipliers, and a period of an optional whole number of units, `s`, `min`, `h` or `day` (with the usual spellings and plurals, and pacer's `m` for minutes). `0.5/s`, `90/min`, `2.5/10s burst 5` and `10000/day` all parse. `parse_pacerd` is unchanged and still refuses `10/d`, so pacerd files read exactly as before; `RateSpec` is the syntax for new configs.

- **Exact.** The count is kept as a decimal, `mantissa / 10^scale` per period, and never passes through a float. A token bucket gets the reduced fraction as its `Rate`: `0.5/s` is one per 2 s and `90/min` three per 2 s, so the limiter's interval is the exact quotient rounded up to a tick. `Display` writes a canonical form (`0.50/sec` becomes `0.5/s`) that parses back to an equal value.
- **Long windows become quotas.** A period of an hour or more without `burst` means "at most N in any window", the usual reading of an hourly or daily quota. A token bucket cannot say that: with a burst of N it grants N at once and then refills N over the window, up to 2N in one window. So such a rate is a `Plan::Quota`, enforced by `rate::Quota` on the sliding `Window` in 16 buckets, which holds each window to the count within the weighting of one bucket. A fractional count takes the shortest whole window: `1.5/h` is 3 in any 2 hours, `0.5/day` is 1 in any 2 days. Shorter periods, and any rate that names a burst, are `Plan::Bucket`s on `Gcra` or a `Table`. The default burst is the count rounded up, as pacer made it the count.
- **Exact waits for quotas.** A denied `Quota::take` says how long to wait, like `Gcra`. `Window::until_at_most(now, n)` finds when the count first drops to `n`: the count never rises while nothing is added, and within each bucket step the weighted oldest bucket `b` counts at most `room` exactly when `b * (slot - into) < (room + 1) * slot`, so the first nanosecond comes out in closed form, one pass over the ring. A test holds it to brute force on 300 random windows: the count at `now + wait` fits and one nanosecond earlier it does not.
- **Within 0.1%, or refused.** A bucket's time per token rounds up to a whole tick of 1/64 ns, so it never grants faster than written and is slower by less than one part in its interval. A rate where that exceeds 0.1%, faster than about 64 million a second, is refused with the slowdown it would have (`2g/s: too fast to enforce within 0.1% (it would run 0.66% slow)`) rather than silently slowed, and so is anything slower than one per 366 days, a period over 366 days, a count over 2^50 or with more than nine decimal places, a rate and burst whose tolerance passes 2^62 ticks, and a fraction whose exact interval does not fit 64 bits. Every check runs in `parse`, so `RateSpec::plan` cannot fail.

`tests/rate.rs` checks this from the text with plain integer arithmetic. Over 2,000 generated rates (counts of up to seven digits and nine decimals, every unit spelling, periods of up to 400 units, with and without burst), each accepted rate is held as exactly the written fraction, each bucket's interval is never shorter than written and at most 0.1% longer, each quota's limit over its window equals the count over the period with the shortest whole window, and each refusal is one of the reasons above for a reason that holds. Two simulations run a greedy client, which takes one at a time and comes back exactly when told to:

- 64 random bucket rates over a simulated day grant their burst plus the day's share of the rate, never more and within 0.1% or one request.
- 64 random hourly and daily quotas grant exactly their limit in the first window and within 0.1% of it in each of the next three, and no window that starts at a grant holds more than the limit plus a sixteenth.

The rates the roadmap names, from an unaligned start: `0.5/s` grants 43,200 in a day against a target of 43,200, `90/min` grants 129,689 (a burst of 90 plus 129,599 of 129,600), and `10000/day` grants exactly 10,000 on each of eight days. The bench gives a quota 150M decisions per second while it has room and 12.5M when spent, each denial computing its exact wait, against 128M for `gcra take` in the same run on a 4-vCPU machine.

### Speed against libpacer

`crates/edgefront-limiter/benches/decisions.rs` runs the single-thread workloads of `bench/bench_limiter.c`: a rate of 10^7 per second with a burst of 1000, time advancing 50 ns per decision, and a 200,000-key table under the evict policy, taking either 10,000 spread keys or one hot key. On one 4-vCPU Intel Xeon at 2.1 GHz, two runs each, in millions of decisions per second:

| workload | Rust, SipHash-1-3 | Rust, SipHash-2-4 | C |
|---|---:|---:|---:|
| GCRA take | 174 to 185 | | 111 to 120 |
| table take, 10k keys | 20.1 to 20.3 | 18.7 to 20.5 | 12.0 to 12.3 |
| table take, one hot key | 46.2 to 48.3 | 47.1 to 47.7 | 37.4 to 38.3 |

Before two changes the table was 15 to 30% slower than the C on the same machine (10.3 and 9.2 million with 10k keys, 31.9 and 27.1 with the hot key). Callgrind showed the Rust running fewer instructions per decision than the C (about 350 against 440), so the gap was stalls, not work:

- **SipHash tail.** The bytes after the last whole block were copied into a zeroed buffer and loaded back as one 64-bit word. That load spans several narrower stores, which the processor cannot forward, so every hash waited for the stores to retire, on the path from key to shard to slot. The tail is now assembled in registers from at most a 4-, a 2- and a 1-byte load. libpacer's byte-at-a-time load never had the stall. This alone doubled the 10k-key rate.
- **Entry alignment.** `Entry` is now `#[repr(align(64))]`, so each of its 64 bytes sits on one cache line and a probe or an LRU relink touches one line per entry. A heap slice of 64-byte values had only 16-byte alignment, and libpacer's `calloc` returns a large table's slots 16 bytes into a line, so three entries in four straddled two lines. This added about 8% with 10k keys and no memory.

The absolute targets of 300 million GCRA and 18 million keyed-table decisions per second come from pacer's own numbers (313 and 19) on its reference machine, the Docker Desktop Linux VM (arm64, 16 vCPUs) on an Apple M4 Max. On that machine (Docker 28.0.4; Rust 1.99.1 and clang 18 in an Ubuntu 24.04 container), on 20 Nov 2026, four runs of each, single thread, in millions of decisions per second:

| GCRA take | 434 to 476 (median 456) | | 346 to 372 (median 360) | 300 |
| table take, 10k keys | 32.0 to 32.8 (median 32.2) | 28.8 to 32.7 (median 31.7) | 20.8 to 24.5 (median 22.4) | 18 |
| table take, one hot key | 107 to 114 (median 113) | 101 to 103 (median 102) | 67.3 to 68.7 (median 68.0) | |

### Admission at accept

`edgefront_limiter::conn` ports pacerd's `admit` from `proxy.c` and the per-listener state from `daemon.c`. One `Admission` per listener is shared by every worker, and `admit(peer, now_ns)` runs pacerd's checks in pacerd's order, before any byte is read:

1. The listener's open count, one `AtomicU32` incremented first and given back on refusal, against `max_conns`: `listener_full`.
2. One `Table::hold` on the client key, with a cap of `per_ip_max_conns` (or no cap) and one token of `per_ip_conn_rate`: `per_ip_conns` at the cap and `per_ip_rate` with no token, both taking nothing, or `table_full` for a new client with no room under the deny policy. With neither limit set the table is not called. A limit that is off is still a table, at pacerd's unlimited rate of 10^9 per second, so a reload can switch it on in place.
3. With `per_ip_conn_quota` set (TOML only; pacerd has no quota), one `QuotaTable::take` on the same key: `per_ip_quota` when the client already opened `limit` connections in the window, or `table_full` for a new client the quota table has no room for. Either refusal refunds the token the hold took, and dropping the refused `Permit` gives back the hold and the slot, so it takes nothing either. The quota comes after the hold because a hold refusal takes nothing and a window cannot give a count back; a refused hold never touches the quota.

The client key is `pd_client_key`: 4 bytes for IPv4 and for IPv4-mapped IPv6, or 16 bytes of IPv6 cut to `ipv6_prefix` bits. An admitted connection holds a `Permit`, whose drop releases the hold and then the listener slot, so a client that saw its connection close and reconnects at once is admitted, as pacerd guaranteed by logging the close only after both. Holds are never reclaimed or evicted, so the evict policy cannot hand an open client's slot to someone else.

pacerd read the caps from the worker's config pointer, so one accept saw one reload. Here `max_conns` and `per_ip_max_conns` share one `AtomicU64`, and the prefix and whether a rate is on share one `AtomicU32`, so each accept reads both caps from the same reload without a lock. `reconfigure` refuses a change of `table_size` or `table_full` with pacerd's message (`listener web: table_size cannot change without a restart`), since the table is fixed memory.

`conn::QuotaTable` is the quota's table, sized and full-policied like the client table: the same shard count for the same `table_size`, `table_full`'s deny or evict, and all memory allocated at start. Each client has a `Window` of 16 buckets, the counter `rate::Quota` uses, and a test holds every client to a `Quota` of its own over 300 seeded scripts where keys outnumber the table, through reclaims and refusals. An entry is 200 bytes, so each shard keeps a pool of exactly its share of entries and a separate open-addressing index of 8-byte `(hash tag, entry)` pairs, at most three quarters full; backward-shift deletion moves those pairs and never an entry, which keeps its place on the shard's LRU list. A full shard reclaims the coldest of its eight least recently used entries whose window is empty, then denies or evicts the least recently used. Every window's buckets start on a multiple of the bucket width (a sixteenth of the window), so an empty window is exactly a fresh one and reclaiming it changes no decision; the alignment is also why two clients seen in the same bucket lose those counts at the same moment. A window ahead of the clock, after a worker's clock read lagged another's, is not empty in that sense and is kept. With the default `table_size` of 16,384 the quota table takes 3.6 MB, beside the client table's 2.1 MB, and a listener without a quota allocates none.

A reload keeps every client's count when only the quota's limit changes, and clears the table when the window changes (buckets of another width cannot carry counts over) or when the quota is switched off or back on. The table exists only for a listener started with a quota, so switching one on where there was none is refused (`listener web: per_ip_conn_quota cannot be switched on without a restart`). `Admission::sweep` sweeps both tables.

`Counters` are pacerd's sixteen per-listener stats, with `pd_stat_names` as `Stat::name`, and `Stat::for_reason` is pacerd's `stat_for`: the close reasons that `edgefront_core::l4::CloseReason::as_str` gives and the refusal reasons map to the same counters as in pacerd. pacerd kept one set per worker, written with plain stores; here every worker adds to one set with relaxed atomic adds, a few per connection, none per byte. Two names are edgefront's own, after pacerd's: the refusal `per_ip_quota` and its counter `rejected_per_ip_quota`, at the end of `Refusal::ALL` and `Stat::ALL` so pacerd's order is kept.

### Byte shaping

`edgefront_limiter::shape` ports pacerd's `reserve` and `give_back`. A listener's `Bandwidth` holds its two byte limits: `per_ip_bandwidth`, one bucket per client in a keyed `Table` sized and full-policied like the client table, and `bandwidth`, one `Gcra` that every connection of the listener shares. A limit that is off is still a bucket, at pacerd's unlimited rate, so a reload switches it on or changes it in place and every client keeps its debt. Both directions of a connection draw on the same buckets.

Before a connection reads from either side, its `Shaper` reserves as many bytes as the buffer has room for. The client's bucket is asked first, with `take_range` and a minimum of 4 KiB (or the whole request if smaller): without the minimum, a connection whose socket is always readable takes each token the moment it appears and slower-waking ones never get one. Then the listener's bucket gives what it can of that, and the rest goes back to the client's bucket, so a client is never charged for bytes the listener held back. When the grant is 0 the connection leaves that direction unread until the retry time, and TCP flow control holds the sender back. Bytes granted and not read go back to both buckets. A new client that the table has no room for (full of active clients under the deny policy) waits 50 ms and asks again; it never gets an unlimited share.

The listener's bucket needs more than a minimum. pacer found (its #238) that a connection that found it short only learned when the next 4 KiB would be free, every waiter was told the same moment, and whichever ran first then took the quantum, again and again: one of two downloads through a 1 MiB/s listener took most of the link. So, as in pacer now, a connection that finds the listener's bucket short books its next quantum there with `Gcra::book`, which takes tokens that are not there yet: the bucket goes into debt, and the booking says when its tokens are due. The connection sleeps until then and reads the booking without asking again, so bookings queue in the bucket's arrival time and waiting connections are served in the order they asked. A connection gives its booking back when its own per-client limit holds the read back (it would otherwise keep the listener's tokens from everyone else), when its client can no longer be tracked, when a reload turns the listener's limit off, and when it closes. Debt from bookings is capped at 2^62 ticks, about 2.3 years, past which a connection waits as before. `Gcra::book` is checked against the exact reference bucket in `tests/model_gcra.rs`, whose level may now go negative down to that cap.

The relay side is `edgefront_core::l4::proxy_paced` and its `Pace` trait: `reserve` before every read (a `Grant::Wait` leaves that direction unread until its time), `give_back` for what the read did not use, `moved` for every read, and a `check` at a deadline. A connection's idle timeout, its two throttles and the check share one tokio timer set to the earliest of them, which is reset only when a nearer deadline appears or it fires, as pacerd kept one heap entry per connection.

The tests run in virtual time. One client held to `per_ip_bandwidth` over 30 seconds of 16 KiB reads with short reads mixed in achieves its rate within 2% past the opening burst, at 512 B/s, 1 MiB/s and 10 MiB/s, and never more than the bucket allows. Eight always-readable connections from different clients share a 1 MiB/s listener within 2%, and none gets less than half its fair share. Two that wake at exactly the same moments, A always first, take turns, where without bookings A takes everything. Eight threads racing reservations never get more than the bursts.

### The slow-client check

`edgefront_limiter::slowloris` ports pacerd's `check_rate`. A slowloris client sends just enough to dodge the idle timeout and holds its slot for ever. With `min_rate <bytes> per <window>` set, each connection's `SlowCheck` counts the bytes it moves, both ways together, in a `Window` of the minimum's length cut into 10 buckets. Once a whole window has passed since the connection opened it is checked every tenth of a window, and one that moved fewer than `bytes` in the last window is closed as `slow_client`. A connection that shaping throttled at any time during the last window is exempt, because the slowness was ours: the shaper records when each throttle ends, as pacerd's `last_throttle` did. A reload applies at the next check: a minimum switched off stops the checks for good, and a new byte count or window length is what the next check compares against, while the window keeps the bucket width the connection started with.

A `SlowCheck` is a fixed 184-byte value with no clock and no timer of its own. The connection puts its `next_check` on its one timer with its idle and throttle deadlines, through `Pace::deadline` and `Pace::check`, as pacerd put the earliest of its deadlines on the worker's timer heap; in tokio that one timer is an entry in the runtime's timer wheel. The tests port `it_timeouts.c`'s three slow-client scenarios at the unit level (a trickler cut after its first window, a client at the minimum checked 141 times in 30 seconds and never cut, and a shaped client never called slow), the exact threshold, bytes leaving the window, reloads, and saturation at the end of the clock. One drives 100,000 connections through a hashed timer wheel of 10 ms ticks for 8 virtual seconds: a third trickle, a third send enough and a third are throttled after every send. Every trickler is cut within one tick of the end of its first window and checked exactly once, nobody else is cut, and each survivor is checked once per 200 ms.

### Running the data path: `edgefront limits`

`edgefront limits -c CONFIG` is pacerd: it reads a pacerd.conf (or the TOML limiter section) and runs its listeners with every limit above, with pacerd's exit codes (2 for a bad config, 1 when it cannot start) and log lines (`msg=ready`, `msg="conn rejected" ... reason=`, `msg="conn closed" conn= listener= peer= reason= bytes_up= bytes_down= ms=`, `msg=draining reason=SIGTERM timeout_ms=`, `msg=drained`), so a script that read pacerd's log reads this one. `-t` checks the config. The pieces are in `crates/edgefront/src/limits`:

- **Accepting.** One task per listener accepts through `edgefront_core::l4::Acceptor`, admits through the listener's `Admission`, and spawns a task per connection that relays with `proxy_paced` and the connection's `ConnPace` (its `Shaper` and `SlowCheck` on the daemon's clock). The close is counted under its reason, the `Permit` is dropped, and only then is `conn closed` logged, so a client that reconnects on reading it is admitted. pacerd's per-worker threads and `SO_REUSEPORT` sockets become one socket per listener on a tokio runtime of `workers` threads; a second daemon on the same port still fails to start, as pacerd made sure with its first bind.
- **Out of descriptors.** A pending connection the process has no descriptor for stays queued on Linux, so the listener stays readable and a naive accept loop spins. `Acceptor` keeps one spare descriptor (`/dev/null`), gives it up, accepts the pending connection and closes it at once, and takes the spare back: the client sees a clean close instead of a hang, counted as `fd_exhausted`. If the spare cannot be had again it stops accepting for 100 ms (`fd_exhausted_paused`). macOS drops the connection that hit the limit inside the failed accept, so there the spare closes the next one queued, if any; the counter is the same. Open connections keep running, and their upstream connects fail as `upstream_socket`.
- **A full client table.** `Admission` refuses a new client with no room in a table full of clients that have connections open, as `table_full`, before reading anything; tracked clients keep their caps and rates, and an entry whose client has nothing open is reclaimed for a newcomer.
- **Drain.** SIGTERM or SIGINT (or `POST /drain`) logs `draining`, stops the accept tasks and drops their sockets, so new connections are refused at once, and waits for open connections to finish on their own. At `drain_timeout` it logs `drain timeout` with the count still open and ends them through each relay's stop future as `drain_timeout`, then logs `drained` and exits 0. pacerd logged the timeout per worker; there is one line here, `worker=0`.
- **Reload.** SIGHUP (or `POST /reload`) re-reads the file and refuses, with pacerd's messages, a change of `workers`, `admin_socket`, the number of listeners, or a listener's name, `listen`, `table_size` or `table_full`, and keeps the running config. Otherwise every listener's admission, byte limits and live config (upstream, timeouts, buffer, minimum rate) change in place for the next connection, and open connections keep their holds and debts.
- **Admin.** The `admin_socket` keeps pacerd's rules (a stale file is replaced, a live one refused, mode 0600, 8 clients, 2 seconds to send a request) but speaks HTTP/1.1: `GET /ping`, `GET /stats` (pacerd's stats text, headed `edgefront version=`), `POST /reload` and `POST /drain`. `edgefront ctl limits [-s SOCKET] stats|ping|reload|drain` is pacerctl over it, with pacerctl's output and exit codes.

`edgefront_limiter::stats` is what the admin API reports. `ListenerStats` is pacerd's stats line: the open count, the 16 counters in pacerd's order (then `rejected_per_ip_quota`) and the client table's size and evictions; the traffic scripts compare every one of them between pacerctl and `edgefront ctl limits stats`. `client` looks one address up under the listener's IPv6 prefix and `top_clients` lists the tracked clients with the most connections open, each with its open count and the tokens left in its connection rate and byte rate and its quota count. They read through `Table::get`, `Table::remaining` and `Table::entries` (one shard locked at a time) and change no entry, recency or counter. `GET /clients?top=N&listener=NAME` and `GET /client?addr=IP&listener=NAME` serve them, and `edgefront ctl limits top [N]` and `client ADDRESS` (with `-l LISTENER`) print them.

Two differences remain. An IPv6 listen address also takes IPv4 clients (as IPv4-mapped addresses, which count as their IPv4 client): pacerd set `IPV6_V6ONLY`, which tokio cannot set without a socket crate the workspace does not take. And pacerd's stats ended with a per-worker `accepted` line; connections are not tied to a worker thread here, so there is none.

`crates/edgefront/tests/limits.rs` runs the binary. With 32 descriptors it holds a few connections, closes further ones at once, uses under a quarter of a CPU over a second with one pending, and recovers when the held ones close. On Linux a table of 16 full clients refuses a 17th address at once while the tracked clients keep their caps. A download shaped to 512 KiB/s takes 30 seconds within 2%. SIGTERM drains 10,000 connections with half their 16 KiB still to come and loses no byte: every client gets every byte in order, every close is `done`, and new connections are refused while it drains. The drain timeout, the admin commands, check mode and the exit codes are covered too. Tests that need another descriptor limit run themselves again in a child under `ulimit -n`.

### The data path, end to end

A connection's path through `edgefront limits`, in order: `Acceptor::accept` (or a shed on the spare descriptor), `Admission::admit` (listener cap, client hold and rate, quota), `l4::connect` to the listener's upstream as configured now, then `proxy_paced` with the connection's `ConnPace`. Each read first asks the `Shaper` (client bucket, then the listener's bucket or the direction's booking) and is reported to the `SlowCheck`; each wait is a throttle on the connection's one timer, which also carries the idle timeout and the slow-client check. The relay ends on `done`, a timeout, an error with its side, `slow_client`, or `drain_timeout` from the drain's stop signal; the reason is counted, the permit dropped, then `conn closed` logged. Memory per connection is the two buffers, allocated once (`buffer`, 16 KiB each by default), plus the task; memory per listener is fixed at start: the client table, the byte table and, with a quota, the quota table, each sized by `table_size`.

`examples/l4_limits.sh` is pacer's live demo run against `edgefront limits` with the same config, peers and checks; it passes on Linux and macOS.

### Address policy

pacer limited each exact address, with IPv6 grouped by one prefix length, and knew nothing else about where a connection came from. Week 5 adds four things, all in edgefront-limiter and used by `edgefront limits` through a config's `[address_policy]` section:

- **Prefix lists** (`cidr.rs`). `PrefixList<V>` maps IPv4 and IPv6 prefixes to values with longest-prefix match. Inserts go into a path-compressed binary radix tree, one per family, with at most two nodes per prefix. Once a list is complete, `compile` flattens each tree into sorted address ranges, each with the value and length of the longest prefix covering it, plus a bucket table: 2^k entries, k up to 20, over the bits just past the ones every range boundary shares. A lookup reads one bucket entry and binary-searches that bucket's few ranges, so a list packed into 2001:db8::/32 spreads over the buckets as well as one spread across the whole space. A range holds its prefix's length, so a lookup builds the match without reading the prefix array. Lists parsed from files and classifiers are compiled; a later insert drops the index and lookups fall back to the tree.
- **Publishing a new list** (`cidr::Swap` and `Reader`). A list is built off the hot path, then published by swapping an `Arc` under a generation counter. Each reader keeps its own `Arc` and its last generation, so a lookup costs one atomic load. Only a reader that sees a new generation takes the swap's lock, once, to pick up the new `Arc`. A reload never makes a lookup wait while the list is parsed and built.
- **Classes** (`class.rs`). A class binds prefixes to `allow`, `deny` or `limit`, with its own `per_ip_max_conns`, `per_ip_conn_rate` and IPv6 grouping. All classes share one prefix list whose values are class indexes, so the most specific prefix of any class decides: a partner's /24 inside a denied /16 is the partner's. A prefix listed by two classes is refused when the classifier is built, since either answer would be a guess. A class sets connection limits only; byte rates stay the listener's, because limiting both a client's and a class's bytes needs a second shaper on every connection, and `per_ip_bandwidth` in a class is refused rather than ignored.
- **Grouping and normalisation** (`key.rs`). An IPv4-mapped IPv6 address (`::ffff:192.0.2.7`) is its IPv4 address everywhere: in the lists, the trusted proxies and the keys. An IPv6 client is keyed by its /64, /56 or /48 (any length from 1 to 128 is accepted), per class, so a host that rotates through its /64, or a customer through its /48, gets one quota, not 2^64.
- **The client behind proxies** (`client_addr.rs`). The forwarding header is `Forwarded` (RFC 7239) or `X-Forwarded-For`, whichever is configured. Reading both would let a client put an address in whichever one the proxy leaves alone. Each proxy appends the address it received from, so the header reads client first and nearest hop last. The walk starts at the peer: while the address in hand is a trusted proxy and entries remain, it takes the rightmost remaining entry, and the first untrusted address is the client. Anything a client writes itself sits left of the entry its first trusted proxy appended, so it is reached only if the client's own address is a trusted proxy. An entry that is not an address (`unknown`, an obfuscated `_node`, a bad port, an unquoted IPv6 node in `Forwarded`) stops the walk at the trusted proxy that appended it; limiting the proxy is conservative, since nothing a client sends can choose another client's key.

`policy::AddressPolicy` puts these together. `decide` resolves the client, classifies it and returns a `Verdict`:

| verdict | when | then |
|---|---|---|
| `default` | no class lists the client | the listener's own limits, keyed by the resolved client |
| `class_allow` | an `allow` class | a listener slot only, no per-client limit |
| `class_deny` | a `deny` class | refused with nothing read |
| `class_admitted` | a `limit` class within its limits | a listener slot, and a hold in the class's own table, given back on close |
| `class_conns`, `class_rate` | a `limit` class at its cap or out of tokens | refused |
| `class_table_full` | the class's table has no room for a new client | refused; class tables refuse rather than evict, so a flood of new addresses cannot push a held client out |

**On the accept path.** With a header configured, `edgefront limits` reads the request head with `peek`, so nothing is taken from the stream and the upstream sees every byte. It reads until the blank line, up to 8 KiB and the listener's `connect_timeout`. A head that is too large, too slow or not HTTP gives no values, so the peer itself (a trusted proxy) is the client. While a connection waits for its head no limit has counted it yet, so at most 4,096 may wait at once and the rest are refused as `listener_full`. Refusals are logged as `conn rejected` with the reason, the class and the client, under pacerd's refusal log limit. `ctl limits stats` adds an `address_policy` line with the lists' sizes and each verdict's count. A reload builds the new policy in full, list files included, before anything changes; a list file with a bad line refuses the whole reload, naming the file and line, and the running policy stays. Class tables start empty after a reload, since their classes and limits may all have changed.

**Measured** on this Mac (Apple M4 Max, macOS, the Rust release profile) with `cargo bench -p edgefront-limiter --bench prefix_list`: a list of 1,000,000 distinct prefixes, nine IPv4 (/8 to /32) to one IPv6 (/16 to /64, from addresses in 2001:db8::/30), and 2,000,000 lookups of random addresses. The clock ticks every 41.7 ns, so lookups are timed in batches of 32 and each batch gives one per-lookup sample. Three runs at load averages 7.6 to 7.9:

| | run 1 | run 2 | run 3 |
|---|---:|---:|---:|
| parse and build, ms | 300.6 | 379.2 | 343.9 |
| reload while a reader keeps looking up, ms | 340.3 | 368.9 | 412.7 |
| independent lookups, p50 / p99 / p99.9 ns | 19.5 / 35.2 / 58.6 | 19.5 / 33.8 / 56.0 | 20.8 / 35.2 / 50.8 |
| dependent lookups, p50 / p99 / p99.9 ns | 45.6 / 119.8 / 181.0 | 65.1 / 136.7 / 195.3 | 70.3 / 153.7 / 201.8 |
| mean of untimed lookups, ns | 14.4 | 15.0 | 16.1 |

The list takes 87.9 MiB, about 92 bytes a prefix. "Independent" lookups are what the accept path does: each connection's lookup is unrelated to the last, so the CPU overlaps their memory reads. "Dependent" lookups each wait for the previous answer, so each pays a full trip to memory; at 88 MiB the list does not fit in cache, and that trip is the cost. The issue's 100 ns p99 holds for the first and not for the second. During a reload the slowest lookup of the reader's 9 to 11 million took 11.8 to 28.5 µs: the reader thread was descheduled, never blocked on the swap. The test `a_million_prefix_list_reloads_in_under_a_second_without_blocking_lookups` checks that a reload costs no more than building the list once in the same run, while a reader keeps looking up, and that no lookup waits for it. The second is the benchmark's to show: the test also runs in debug and under ThreadSanitizer, where the same reload took 36.7 s on a CI runner.

**Tested against references.** `cidr` checks the tree and the compiled index against a linear scan on random overlapping prefixes, probing every range edge, plus a 60,000-prefix packed list against the tree. `class` checks 10,000 random overlapping prefixes in random classes against a scan for the most specific. `key` rotates 10,000 addresses inside one /64, /56 or /48: they give one key and one burst of a rate, where keyed by full address all 10,000 would have been admitted. `client_addr` covers spoofing (forged entries on the left, forged trusted addresses, an untrusted peer with any header), RFC 7239's grammar and every malformed case, and a proptest that whatever a client prepends, the answer is the entry the trusted proxies appended. Fuzz targets `forwarded` and `cidr_list` run 30 minutes each in CI. `tests/e2e_address_policy.rs` runs the binary behind two trusted proxies.

### HTTP limits

pacer saw only TCP bytes, so it could not limit a login path, an API key or failed requests. Week 6 adds request-level limits in edgefront-limiter's `http` module (behind the default `http` feature, which brings in edgefront-core and edgefront-proxy; without it the crate is still serde alone), attached to the proxy's routes as an `edgefront_core::filter::Filter`, the same seam the cache uses. Keys are typed selectors for now; they move onto the shared rules engine in proxy week 14.

- **Rules** (`config/http_limits.rs`). Each `[[http_limits]]` rule has a name, the routes it attaches to (by index, all by default), a match on host, path, path prefix and methods, a key, a `RateSpec` token bucket, the statuses it counts, an action and a refusal response, and its own `Table`. `HttpLimiter::route_filters` gives each route the rules that apply to it, at most 16; a route without rules has no filter and pays one branch.
- **Keys** (`http/key.rs`). Each selector writes its field's value into a 32-byte key on the stack: a value byte as itself except 0 (written `0 1`), and each value ends `0 0`, so the encoding is prefix-free. A key that would pass 31 bytes is hashed as it is written by two SipHash-1-3 states with the rule's own random keys, into 32 bytes; since every written key is shorter, the two forms cannot meet. Paths are the decoded, cleaned path routing matched on (`edgefront_proxy::path`), hosts lose case, port and trailing dot, and query values are percent-decoded, so a client cannot spell its way to a new bucket. A repeated header, cookie or parameter writes a marker (`0 2`) instead of a value: every such request shares one bucket, because the upstream may read any one of the copies, and keying on the first would let a client put a fresh value in front of the one the upstream uses. A missing field means the rule does not apply, as with Envoy descriptors.
- **The request phase** (`http/layer.rs`) reads the clock once and walks the route's rules in order: match, key, `Table::take_reset` (a take that also returns the time to a full bucket under the same lock, for the headers). A refused take does what the action says. `block` answers with the refusal and refunds what earlier rules took, so a request refused by one rule spends nothing in another. `delay` books the token with `Table::book` (into debt, like `Gcra::book`) and sleeps until it is due, if that is within `max_delay`; waiting requests are served in the order they asked, and one whose booking came out past the limit gives it back and is refused. `log` lets the request through and counts it.
- **Counting on responses** (`http/response_count.rs`). The token is taken on arrival and settled in the deliver phase: a status outside `count` refunds it. Taking first is what stops a burst of concurrent password guesses, which would all pass a check-then-charge scheme while their answers were in flight. The status is the one the client gets, a proxy-written 502 included; a request whose client hung up before the response keeps its token. `Gcra::refund` never moves a bucket before now, so refunds cannot bank tokens.
- **Headers** (`http/headers.rs`), per draft-ietf-httpapi-ratelimit-headers-11. A GCRA bucket of `burst` tokens refilled one per interval maps to `q` = the burst and `w` = the time a whole burst takes to refill, rounded up (the draft's `w` is an integer and informational). `RateLimit`'s `r` is the tokens left; `t`, the draft's effective window ("the client can use no more than `r` within `t`"), is the time to the next token, rounded down so the statement stays true, and absent for a full bucket. Whole seconds are coarse for limits of several a second, so the item carries the same wait in milliseconds, rounded up, as the vendor parameter `edgefront-ms`, which the draft allows as a comment. `Retry-After` on a refusal is the exact `retry_after_ns` rounded up to whole seconds, never early. `headers_match_exact_gcra_retry_times` takes each header's wait at four rates and checks that a request a millisecond early is refused and one at the time admitted.
- **Lints.** `edgefront check` builds the rules (each mistake as `http_limits[i].field: reason`) and adds four classes: `http-key-never-matches` (a key prefix, or the match's `path`, outside the match's `path_prefix`), `http-key-host-header` (HTTP/2 requests carry `:authority`), `http-count-own-status` and `http-delay-unused`.

**Measured** on this Mac (details and raw results in [docs/benchmarks/http-limits.md](benchmarks/http-limits.md)). In the proxy pipeline (`benches/http_layer.rs`, requests through `filter::run` with and without the limiter, alternately, 100,000 keys) the limiter adds 709 to 750 ns at p99, 542 to 583 at p50. End to end, `edgefront-bench run` at 50,000 requests per second over 100,000 paths, the limited proxy's p99 was 0.266 ms against 0.256 in the quiet run, and the table of 1,048,576 keys took the RSS from about 20 to 155 MiB. For accuracy, `edgefront-bench http-limits` replays the scenario's own requests at their due times through the same rules: two runs matched it to three requests in 1,500,000; one run that fell four seconds behind schedule under a load average of 24 to 27 refused 1.2% more, because its requests no longer arrived when they were due.

### Several limits, descriptors, costs and hot keys

Week 7 makes a request answer to several limits at once, with costs other than one, and keeps one popular key from serialising the cores.

- **All or nothing** (`multi.rs`). `take_all` takes from each limit in the order given, a lock-free `Gcra::take` or one shard-locked `Table::take` each, with no lock held across limits, so nothing can deadlock. The first refusal stops the walk and refunds every earlier take, newest first. The refund is exact: it runs at the same `now` as the take, and a take of `cost` added exactly `cost` intervals of debt, which a refund at that time removes. Between a take and its refund another request can see the token gone and be refused; that errs towards refusing, and putting the limit most likely to refuse first keeps it rare. `sixteen_threads_take_from_all_or_none` and a proptest run 16 threads, each request on four random shared limits and one key, on a clock that does not move: at the end every bucket has given out exactly one token per admitted request that named it.
- **Descriptors** (`descriptor.rs`, `descriptor/yaml.rs`). The tree and the decisions follow envoyproxy/ratelimit: at each level the child for `key_value`, else the first wildcard value that matches (`*` any run, several allowed), else the key alone; the limit is the one on the node the last entry reaches. Counters are fixed windows aligned to the Unix epoch, keyed by the domain, every entry and the window start, incremented by the request's hits even when it is over, as the service's `INCRBY` is, and over the limit past `requests_per_unit`; `shadow_mode` counts without refusing, `replaces` drops a named limit when a request matches the one replacing it, and `share_threshold` keys a wildcard's counter by its pattern. The YAML is read by a small parser of the subset these files use (block maps and lists, scalars, flow collections, comments), since the workspace takes no YAML dependency; anchors, tags and block scalars are refused with their line. The service's `basic_config.yaml` and `wildcard.yaml` are vendored under `tests/data/envoy_ratelimit/` and every `GetLimit` case its `config_test.go` asserts on them gives the same answer, as do its error messages for each mistake (empty domain or key, duplicate composite key, bad unit, replaces itself or empty, unknown or non-string keys, unlimited with a unit).
- **Costs** (`cost.rs`). A cost is fixed, the request's `Content-Length`, a GraphQL complexity or an upstream header charged after the response. GraphQL is scored as GitHub scores it: each field 1, and a field with `first`, `last` or `limit` multiplies what is under it, with fragments expanded and depth, size and multipliers capped; a query that cannot be scored costs 1,000. The proxy's filters see headers, not bodies, so the layer scores a GET's `query` parameter; a POST body is scored by a caller that has it. A cost charged after the response takes nothing at first (a request is refused only while its key is in debt), then books the header's number, a burst at a time, so the debt holds back the key's next requests. A cost above the burst can never be admitted and is refused with a full refill as its retry.
- **Hot keys** (`hotkey.rs`). `HotTable` wraps a `Table`. Each thread's `Handle` samples one decision in 256 into a 64-slot space-saving counter; every 2,048 samples a key with 5% of them is made hot and one below half that is cooled, and the counts halve. A hot key gets a `SplitBucket`: one GCRA per thread slot on its own cache lines, each the rate's tokens per `n` periods with a share of the burst, the shares summing to it. A decision takes from its own slot, then once from the next; a cost larger than a share is gathered from all of them, all or nothing. Every millisecond of clock the first thread past the mark moves tokens from the fullest slots to the emptiest, keeping the total, so uneven threads do not leave tokens stranded; between rebalances a split can lag an exact bucket by under one token per slot. A key made hot starts with the tokens its entry had, and decisions the table took while the split was being made are charged to the split once it is published, so only a decision already past its hot-set check at that moment (one per thread at most) escapes it. The hot set is published through `cidr::Swap`, one atomic load per decision.
- **NGINX bursts** (`burst.rs`). `limit_req`'s leaky bucket in NGINX's units: milliseconds, the rate in thousandths of a request a second, excess in thousandths of a request. A key's first request starts it with no excess; later ones add 1,000 less what drained, are refused past `burst * 1000`, and pass after `(excess - delay * 1000) * 1000 / rate` ms. NGINX's documented example (`rate=1r/s burst=5`, six at once: one now, five a second apart, a seventh refused) and its clock handling (back by under a minute counts as no time, by more as one millisecond) are tests. The HTTP layer's `delay` action is the same queue on the GCRA: a request books its token and waits for it, up to `max_delay`.

**Measured** on this Mac ([docs/benchmarks/hot-key.md](benchmarks/hot-key.md)): one hot key among 10,000 cold ones at 16 threads made 17 to 22 million decisions a second on one bucket and 115 to 279 million split, at load averages of 24 to 109.

### Penalty box, bans and overload mode

Week 8 stops evaluating clients that keep hitting their limits, and protects the process itself when the host runs short.

- **The penalty box** (`penalty.rs`) counts a rule's refusals per key in windows of `window`. Refusals in `windows` consecutive windows box the key for `timeout`, doubled for each repeat offence up to `max_timeout`. A key clean for `forget` after release starts over. Entries are 64-byte slots in 64 shards, addressed by the key's SipHash with a probe of 8, so a check is one hash, one lock and a few adjacent slots. A full probe replaces the entry released first: a flood of fresh keys can release a boxed key early, but never boxes one that was not refused.
- **Bans** (`ban.rs`) compare their end with the caller's clock, so a ban ends on its nanosecond. A wheel of 1,024 slots of 10 ms drops ended bans in time proportional to the bans ending: a sweep visits only whole ticks that have passed, and a ban further out than one turn waits in its slot for the turn it ends in. Bans persist as `<unix ms> <hex key> <reason>` lines, written to a temporary file and renamed. Times convert through the clock's wall-clock offset, since the monotonic clock starts over with the process. `edgefront limits` keeps one list for the life of the process, so a reload does not touch it. HTTP rules ban `rule \0 key`, and `HttpLimiter::with_bans` hands the list to a rebuilt limiter.
- **Listener-wide rates** (`listener.rs`) are a GCRA for connections, one for requests, and an in-flight counter whose guard gives the place back on drop. With `[listener]`, the HTTP limiter puts a filter on every route and checks the request rate and in-flight cap before any rule, holding the request's place in its settlement until the response is delivered. Connections are decided by `Handler::admit_connection`, a default method of the listener's handler trait that admits everything unless a handler says otherwise, and `Proxy::with_connection_gate` gives the limiter's connection rate to it.
- **Overload** (`overload.rs`) reads the `some avg10` line of PSI files, and the cgroup's `memory.current` against `memory.max`. It steps up as soon as a reading passes a level's threshold. It steps down one level only after readings have stayed under the threshold less the hysteresis for the dwell, so a load hovering at a threshold changes level once, not every sample. On each change, every registered table is reconfigured to a half or a quarter of its base rate and burst, and keeps each key's debt as time. A client well within its limit is unaffected; the ones using most of theirs are shed.
- **Connection quotas.** The mechanism is the listener's: `edgefront_core::listener::ConnQuota`, given by a handler through `Handler::conn_quota` (none by default, so other handlers are untouched) and set on the proxy with `Proxy::with_conn_quota`. Each connection counts the requests it starts and the bytes its stream reads and writes. The request that reaches the quota is the last: over HTTP/1.1 its response says `Connection: close`, and the connection is finished as a drain finishes it, which over HTTP/2 sends GOAWAY. `conn_quota.rs` reads and checks the `[connection_quota]` section.

**Measured** ([docs/benchmarks/overload.md](benchmarks/overload.md)): a boxed key's check takes 23 to 56 ns at p99. In-process, under synthetic CPU saturation (four workers at their whole capacity, good clients at a fifth of their limit and abusive ones at nine tenths), overload mode held the good clients' p99 to 0.23 to 0.25 ms, against 20 to 225 ms without it, by holding the abusive clients to half their limit.

### Shadow mode and policy replay

Week 9 lets a limit prove itself before it enforces.

- **Modes** (`shadow.rs`). A rule's mode is an atomic beside it. A shadow rule takes its tokens exactly as an enforcing one would, so its table goes through the states an enforcing copy goes through on the same traffic. A request it would refuse is counted, and one in 64 is kept as an example (time, a hash of the key, the wait). Nothing else happens to the request: no response, header or delay, and no other rule's tokens refunded. `off` skips the rule. `HttpLimiter::apply_modes` takes the next config's rules, refuses them unless they differ only in mode (anything else needs new tables), and stores the new modes, so promotion keeps every key's state. `edgefront proxy` polls its `--limits` file's mtime each second and applies such a change. Because the proxy refuses reloads while filters are attached, this is the one change a running proxy takes. `tests/replay_equivalence.rs` holds the shadow count equal to an enforcing copy's refusals, request by request, over 1,000,000 generated requests and a proptest of 16 seeds. The lint `http-shadow-shadowed` flags a shadow rule after an enforcing rule that is at least as strict on the same routes, match and key: that rule refuses first, so the shadow rule never sees those requests and undercounts.
- **Recording** (`record.rs`). Each decision is 32 bytes: time, rule index, outcome (allowed, refused, would refuse), cost, and the key's 128-bit hash under two random SipHash keys that the recorder never writes. Equal keys stay equal within a recording, but nothing in it can be read back as a key. The request path pushes onto a bounded ring under a mutex. A full ring drops its oldest record and counts it, so recording never blocks or grows. A task flushes the ring every second, and at exit, to `decisions-NNNNNN.rec` files with a header naming the rules, closing a file past `file_bytes` and keeping `files` of them.
- **Replay** (`replay.rs`). Records are sorted by time and replayed per rule into a fresh table at the candidate's rate, burst and cost, at their recorded times: a virtual clock, so an hour replays in about a second. A recorded would-refuse counts as a refusal before. Keys are the recorded hashes, so a candidate can change a rule's rate, burst, cost or mode, but not what its key is built from. Recorded rules with no candidate, and candidates with no records, are listed. `edgefront ctl limits replay` prints the per-rule table and the top changed keys, and writes the whole report as JSON.

**Measured** ([docs/benchmarks/shadow-replay.md](benchmarks/shadow-replay.md)): 10,000,000 records (305 MiB) read and replayed in 0.63 to 1.05 s. Recording added 38 to 68 ns per request in the pipeline benchmark, at most 0.16% of the 43 µs of CPU a request costs the limited proxy at 50,000 requests per second.

## What cachet is for

cachet is a shared HTTP cache that sits in front of one or more origins, close to clients. It should follow the HTTP caching rules closely enough that an origin can control it entirely through standard headers, keep the origin's load flat when popular objects expire, keep serving when the origin is slow or down if the origin allows it, and let an operator remove content from every node with one request.

It is a single binary with no external services. A node keeps its cache in memory with an optional disk tier, and nodes coordinate only to spread purges.

It does not terminate TLS, speak HTTP/2 or HTTP/3, run edge code, rewrite cache keys, or fetch from other nodes before the origin. Each of these is real work that a production edge needs, and each would hide the parts this project is about.

## Cache settings per route

The cache is becoming a layer that each proxy route turns on, so its settings are per route too. The `[cache]` section is the global block: besides the store's sizes it holds `max_object_bytes`, `max_variants`, `heuristic_max_secs`, `slice_bytes` and an optional `max_ttl_secs` (a cap on any stored response's freshness lifetime), and every route inherits them. `[cache.compression]` turns on gzip, brotli and zstd variants of text-like responses for every route, and a route's own `compress` overrides it. A `[[cache.routes]]` entry names one proxy route by `host` and `path_prefix` and may override any of those five; `enabled = false` keeps the entry but bypasses the cache. A route with no entry bypasses the cache.

`CacheConfig::resolve` ties the entries to the proxy's routes and returns each route's effective `RoutePolicy`, or every problem it found (up to the proxy config's 20), each with its field path in the proxy config's style: `cache.routes[2].max_variants: must be between 1 and 8, got 9`. An override may only tighten what the store allows (`max_object_bytes` and `max_variants` are bounded by the global values the store is built with), lifetimes are capped at a year, hosts compare without case and path prefixes exactly, two entries for one route are refused, and an entry that matches no route is an error, so a typo cannot quietly leave a route uncached. The heuristic cap is held under the route's lifetime cap, so a guessed lifetime never outlasts an explicit one.

## Request phases: the cache as a route layer

`edgefront_core::filter` defines the phases a layer runs in on a proxy route. It lives in edgefront-core so that neither edgefront-cache nor edgefront-proxy depends on the other. A `Filter` is attached per route in a `RouteFilters` table. A route without one skips the phases, so bypass costs one branch. For a route with a filter, a request goes through three phases:

1. **Request**, after routing and before the upstream pick. `Filter::request` sees the route index, method, URI and headers, and may change the headers that go upstream. It returns `Decision::Respond` (the answer, final) or `Decision::Forward`, optionally with an `Exchange` that holds the request's state.
2. **Upstream response**, when the upstream's head arrives and before any of it reaches the client. `Exchange::upstream_response` returns the response to send on.
3. **Deliver**, once, on the response the client gets. `Exchange::deliver` also sees responses the proxy wrote itself (`Delivery::Generated` with a reason such as `connect` or `timeout`), so the cache can answer an upstream failure with a stale copy.

`filter::run` drives the phases around an upstream call. Tests use it, and so can a server that has nothing of its own between the phases.

`edgefront_cache::layer::CacheLayer` is the cache as such a filter. Each route has its own `RoutePolicy`, and `CacheLayer::route_filters` attaches the layer only to cached routes. The phases do what cachet's `proxy.rs` does for one request:

- **Request phase.** Lookup, then the four freshness outcomes. A fill strips the client's conditionals and `Range` and adds the stored copy's validator. `only-if-cached` gets `504`. `no-store`, `HEAD` misses and other methods pass through.
- **Upstream response phase.**
  - A matching `304` refreshes the copy. For a `304` about another representation, the layer returns `Upstream::Resend` with its validators removed. The server sends the request once more, without a body, and gives the new response back to the same exchange. A second `Resend` is answered with a `502` the server writes (`resend_limit`).
  - A storable body is read within the route's `max_object_bytes` and `body_timeout`, then stored under the purge epoch taken in the request phase.
  - A larger body streams through unstored.
  - A successful unsafe method invalidates its URL and its same-host `Location` and `Content-Location`.
- **Deliver phase.** `stale-if-error` replacement, and `Cache-Status` on everything.

A route's `max_ttl` caps every stored lifetime, its heuristic cap applies, and its `max_variants` limits variants per URL through `Cache::store_limited`.

**Collapsing.** Concurrent fills of one URL share one upstream request, through `Collapser::lead_or_follow`.

- The first request leads. It goes upstream as usual, and its exchange publishes the result once it has one: a stored object, a response only it could use, or a failure.
- The others follow. They wait in their request phase, then answer from the published object (`collapsed` in `Cache-Status`) or share the failure, served stale where `stale-if-error` allows.
- A follower goes upstream on its own when the result was not storable, or is a variant its request would not select.
- In cachet the shared fetch ran on a task of its own. Here it is part of the leader's request, so a leader whose client goes away drops the flight, and a follower leads instead.
- An error the proxy wrote about the leader's own request, such as a `400` for its body, is not shared, and its followers go upstream themselves.

**Background refresh.** A copy inside its `stale-while-revalidate` window is answered with `Decision::Refresh`: the client gets the stale copy at once, and the request goes upstream in the background, leading the URL's flight, so there is one refresh per URL at a time.

**In the proxy.** `Proxy::with_filters` attaches a `RouteFilters`; the router maps each request to its route index and its cluster. The phases sit in `Proxy::handle` as follows:

- The request phase runs right after routing, before `max_requests`. A hit takes no place under the limit and never touches an upstream.
- The upstream-response phase runs before the proxy adds the request ID, so a stored response never carries another request's ID.
- The deliver phase runs on everything, including the proxy's own errors. These are named by their steer code (`bad_gateway`, `upstream_timeout`, `no_healthy_upstream`, `overloaded`, `bad_request`), and the cache treats only the 5xx ones as upstream failures.
- A refresh runs on its own task. It takes a cluster permit and the cluster timeout like any request, carries the client request's ID, and has no body.

`Via` and the forwarding headers stay with the proxy.

## Checking the cache against cachet 0.1

Moving the cache onto the shared runtime must not change anything a client sees, so `edgefront-difftest cache` (`make difftest-cache`, in CI on every push) replays a request log against cachet 0.1 and the edgefront binary and diffs every answer. cachet 0.1 is commit `ed77c32`, the last one before the workspace split: the repository has no release tags, so the Makefile pins the commit, exports it under `target/` and builds its `cachet` binary there.

The log is JSON lines, one request each, with a logical time in seconds, a target (a node's proxy or admin listener, or an origin event) and the method, path, headers and body. `cache-record` writes the log a seed generates. The 50,000 generated requests of a run cover about six logical hours across 16 route families, chosen by a skewed popularity:

- Fresh and stale hits, ETag and Last-Modified revalidation, and heuristic freshness.
- `Vary` on two headers, `no-store`, `private`, `no-cache`, `s-maxage`, `Expires` and `Set-Cookie`.
- Objects over the size limit, redirects and errors.
- Byte ranges, valid and not; client conditionals; client `Cache-Control` and `Pragma`.
- `Authorization` and cookies; HEAD and unsafe methods; three spellings of the host.
- Purges by tag and URL, refused purges, origin content changes, and origin outages that `stale-if-error` covers.

Each node runs the same config against its own copy of a deterministic origin, whose answers depend only on the request, the log's clock and the events so far. For each request the runner compares:

- the status;
- every header except `Date`, with the values of a repeated header in order (a request id the node made up is compared only as "generated");
- the body's SHA-256;
- how many requests the node sent its origin to answer it, which catches a revalidation or collapsing change that the response alone would hide.

Two things make a divergence a behaviour change and never noise:

- **Time.** Ages, lifetimes and `ttl=` are whole seconds measured on the wall clock, so two nodes a few microseconds apart could disagree near a second boundary. Each node runs with libfaketime preloaded, reading a frozen wall-clock time from a file that the runner rewrites when the log's clock moves. Monotonic time is left real, so timeouts and health checks behave normally.
- **Eviction.** The memory store picks shards and eviction candidates with a per-process hash seed. The nodes get a budget whose single shard holds the whole generated working set, so nothing is ever evicted.

Requests go one at a time, and a store completes before its response is sent, so the order is fixed too. `crates/edgefront/tests/difftest_cache.rs` runs the harness against the binary itself and must find nothing. It also runs it against a wrapper that sets `max_variants = 1` and a one-minute heuristic cap, and must catch that change, naming the lines and differences. A node that is not on the logical clock is refused before the run starts.

## Following one request

A request is handled in `proxy.rs`, which since W02 is a front over `CacheLayer`. The node answers some requests itself before the cache sees them:

- a request that already passed through this node (`508`);
- a target over `max_uri_bytes` (`414`);
- a request without a host (`400`);
- a body over `max_request_body` on a request that passes through (`413`).

Everything else goes through the layer's phases (`filter::run`) on a single route whose policy is the `[cache]` settings. The upstream is the origin pool. Requests get hop-by-hop headers removed, plus `Via`, `X-Forwarded-For` and the request ID. A failing origin is reported to the layer by name (`connect`, `timeout`, `protocol`, `body-too-large`).

The layer marks each response with its `Outcome` for the requests counter and the access log. It reports the other counters (not stored, streamed uncached, collapsed, background refreshes) through `Observer`, which cachet's `Metrics` implements. It adds the node's `Via` to responses that pass through unstored.

The cluster tests (`tests/cluster.rs`), `tests/revalidation.rs`, `tests/proxy.rs` and `tests/failure.rs` run against this layered node unchanged. `make difftest-cache` holds it to cachet 0.1's answers, request for request.

GET and HEAD go through the cache; every other method passes through to the origin. A request with `Cache-Control: no-store` also passes through.

For GET, the node computes the primary key (lower-cased host plus the request target), looks up the stored variants for that key, and picks the newest one whose Vary selecting headers match the request. The freshness rules in `policy.rs` then decide one of four things: serve it (fresh), serve it because the client accepts staleness (`max-stale`), serve it and refresh in the background (`stale-while-revalidate`), or validate it with the origin first.

Misses and validations go through the collapser. The origin request strips the client's own conditionals and Range, because its result may be shared; the node answers those itself from the stored copy afterwards. When a stored copy exists, the request carries its validator (`If-None-Match` from the entity tag, otherwise `If-Modified-Since`). A 304 whose entity tag matches refreshes the stored headers and freshness; a 304 for some other representation triggers a plain fetch.

Every response carries `Cache-Status` (RFC 9211), for example `edge-a; fwd=stale; fwd-status=304; stored; ttl=60`, and an `x-request-id`. A caller's request id is kept only if it is short and plain, so clients cannot put arbitrary text into the logs.

## Which HTTP caching rules apply, and where cachet is stricter

`policy.rs` implements the shared-cache parts of RFC 9111. A response is stored only if the method is GET, the status is final (any code from 200 to 599 but 206, which is stored only as slices, and 304), neither side sent `no-store` (unless `must-understand` applies, which also needs a status the cache understands), it is not `private`, `Vary` is not `*`, and it has explicit freshness, `public`, or a heuristically cacheable status. A request with `Authorization` is stored only with `public`, `s-maxage` or `must-revalidate` (section 3.5).

A 5xx stored this way never replaces a good stored copy, so `stale-if-error` can still answer with that copy. The directives come from `CDN-Cache-Control` (RFC 9213) when the response has it and it parses as a Structured Fields dictionary; then `Cache-Control` and `Expires` are ignored for this cache's own decisions and still passed on. A targeted field that does not parse is ignored as a whole, and a directive in it with the wrong type (a string `max-age`, say) on its own.

Freshness comes from `s-maxage`, then `max-age`, then `Expires` minus `Date`, then ten percent of the time since `Last-Modified`, capped at a day by default (sections 4.2.1 and 4.2.2). Age follows section 4.2.3 exactly, including the response delay correction, and time running backwards is clamped rather than underflowing. Cache-Control parsing accepts quoted arguments, takes the first of duplicated directives, clamps overflowing delta-seconds to 2^32 - 1, the greatest integer it conveniently represents (section 1.2.2 asks for at least 2^31), so an `Age` just under 2^31 with `max-age=4294967295` is still fresh, and treats an unparseable `max-age` as zero, which makes the response stale rather than fresh forever.

Some choices go beyond or narrow the RFC, on purpose:

Responses with `Set-Cookie` are not stored. The RFC allows it, but sharing one client's cookie with everyone is almost never what an origin meant.

Responses that can never be reused (no freshness, no validator, no stale allowance) are not stored, since they would only take space.

Qualified `no-cache="field"` and `private="field"` are treated as their unqualified forms. That is the conservative reading.

Ranges are answered from the stored copy, after the preconditions and only when the answer would otherwise be 200. A request may name up to 16 ranges. Ranges that overlap, or lie within 80 bytes of each other (about one part's headers), are sorted and merged, which RFC 9110 section 15.3.7.2 allows in any order. Otherwise the parts keep the order the client asked for. One remaining range is a plain 206 with Content-Range. Several are `multipart/byteranges`: each part carries the representation's Content-Type and its own Content-Range, under a boundary drawn per response. Ranges an object cannot satisfy are dropped, and 416 comes only when none is left. Two caps stop a Range header from costing more than the object. More than 16 ranges, or ranges adding up to more than twice the object's length before merging, are ignored, and the whole object is served with 200, as section 14.2 permits for many small or overlapping ranges. The `range` fuzz target holds the parser to this: parts inside the object, sorted out of any overlap, no more than 16, and no more bytes than the object has. Partial responses (206) from the origin are never stored; the node always fetches the whole object and answers ranges from it.

HEAD misses pass through to the origin without being stored. HEAD hits are answered from the stored GET response.

HTTP dates are accepted in all three formats with day names, month names and `GMT` in any case, and an rfc850-date's two-digit year is read as the nearest year with those digits no more than 50 years ahead (RFC 9110 section 5.6.7). An `Age` field line holding a list is read by its first member. `If-Modified-Since` on a hit compares with `Last-Modified`, or without it the stored `Date`, or without that the time the response arrived (RFC 9111 section 4.3.2).

Unsafe methods that succeed invalidate the target URL and same-host `Location` and `Content-Location` URLs (section 4.4). Only the local node is invalidated; each node sees its own writes.

### Conformance: the http-cache-tests suite

`tests/conformance.rs` runs the open http-cache-tests suite (github.com/http-tests/cache-tests, the suite behind cache-tests.fyi) against the binary as a shared cache: the suite's server is the origin, the binary is in front of it with its defaults, and the suite's command line sends every test that is not browser-only through it, 475 in all. Each result is classified by the suite's own rules (`tests/conformance/classify.mjs` calls its `determineTestResult`), and the run must match `tests/conformance/allowlist.toml` exactly: a required or optimal test that does not pass must be listed with the result it gives and a reason, and a listed test that starts passing, or fails another way, fails the run until the list is updated. Behaviour checks (yes or no about an optional behaviour) are shown but not judged.

The suite is third-party Node code, so it runs only in the `conformance` workflow on GitHub's runner, checked out at a pinned commit with its one runtime dependency (undici, at the version its package.json pins) and Node 26. The test is ignored in ordinary `cargo test` runs. The job writes the suite's raw results, the classification and a summary as the `http-cache-tests` artifact, and the summary into the job page.

The first run, on Node 22, found 45 required or optimal tests not passing. Four of them were the interim-response tests timing out inside the suite's own client, even against its own server, which is why the job runs Node 26. These were bugs, now fixed and covered by unit tests:

- `CDN-Cache-Control` was ignored (13 tests, 6 of them required).
- An `Age` of `7200, 0` was read as invalid, so 0, and a stale response was served as fresh.
- Final statuses outside a fixed list (299, 400, 500, 502 to 504, 599) were never stored, even with explicit freshness or `public`.
- `max-age` was clamped to 2^31, so an `Age` just under 2^31 made a response with `max-age=4294967295` stale.
- `Expires` with a day, month or `GMT` in the wrong case was refused, and an rfc850 `Expires` 44 or 48 years ahead was read as the 1970s.

What is left is listed, by design or for later: responses with `Set-Cookie` are not stored (2 tests); a 206 is stored only as slices, never on its own (5); `Accept-Language` is not normalised for `Vary` (3); POST responses are not reused (1); a 1xx from the origin is not forwarded, because hyper's server cannot send one (4, one of them required; 103 Early Hints are week 7, #96); and `If-Modified-Since` without `Last-Modified` is judged against the stored `Date`, as RFC 9111 section 4.3.2 says, where the suite expects a 304 (1). That leaves 177 of 179 required tests passing and 137 of 151 optimal ones.

## Many clients, one origin request

`collapse.rs` is a single-flight map from cache key to an in-flight fetch. The first caller starts the fetch on its own task and every caller, including the first, waits on a watch channel for the result. Running the fetch on a separate task matters: if the first client disconnects, the fetch is not cancelled, the followers still get an answer, and the response still reaches the cache. A panic in the fetch drops the channel, which releases every waiter with an error, and a drop guard removes the key. The result is published before the key is removed, so a request arriving in that gap reads the result instead of starting a second fetch.

**Streaming while filling.** A storable response that declares a `Content-Length` over 64 KiB (and at most the per-object limit) is not buffered before anyone sees it. The fill pushes each chunk into a `fill::Filling` as it arrives, and the leader's client reads from it at once. The flight is published with the growing body and held open until the body is in (`Lead::publish_held`), so a client that arrives halfway through follows it too. That client is handed every chunk already received, then the rest as it comes. When the last byte is in, the fill stores the object and ends every reader's body. If the origin fails partway, sends more or fewer bytes than it declared, or passes the body timeout, the fill aborts: every reader's body fails with the reason, so each client sees a broken connection rather than a short body taken for whole, and nothing is stored. A follower whose request carries conditionals or a range, or another Vary variant, waits for the whole object and is answered from it as before. Smaller bodies are still read whole first, which costs a client almost nothing. `crates/edgefront-cache/tests/streaming_fill.rs` runs it over real TCP. An origin sends the first 1,000 bytes of a 200,000-byte body, then holds the rest for half a second. A client that arrives in between gets its first byte within 50 ms of the origin's, then the whole body; the origin sees one request, and the next request is a hit. A ranged follower gets its 206 from the stored object. An origin that dies halfway fails both clients and leaves nothing stored.

Sharing is limited by what the response allows. A storable response is shared, and every waiter may use it. A response that may not be stored (for example `private` or carrying `Set-Cookie`) was produced for the first client's request, so only that client receives it; each follower then makes its own request. A follower whose Vary selecting headers do not match the shared response also fetches on its own. A test sends ten concurrent requests with different cookies to a `private` URL and checks that each client gets its own body.

## Serving stale content (RFC 5861)

Inside the `stale-while-revalidate` window the stale copy is served at once and one collapsed background refresh starts; further requests during the refresh are served stale without starting more refreshes.

When revalidation fails with a connection error, a timeout, a broken response, or a 500, 502, 503 or 504, the stale copy is served if the response's or the request's `stale-if-error` window covers its staleness. Other statuses, such as 404, are answers and are passed on. `must-revalidate`, `proxy-revalidate`, `s-maxage` and `no-cache` turn off every form of stale serving, as RFC 9111 section 4.2.4 requires.

## Keeping the right objects in memory: S3-FIFO with a byte budget

The memory tier (`store/memory.rs`) uses S3-FIFO from Yang et al. (SOSP 2023). New objects enter a small FIFO queue. When the small queue is over its share (ten percent of the bytes), its oldest object either moves to the main queue, if it was read since it was inserted, or is evicted and its key hash recorded in a ghost queue. An object whose key is in the ghost queue skips the small queue on its next insert. The main queue evicts its oldest object, giving it another round for each recorded read, with the count capped at three.

I chose it over LRU and over TinyLFU (Einziger, Friedman and Manes, 2017) for three reasons. A hit only bumps a two-bit counter, so lookups take a shared lock and never reorder a list, which is what an edge cache does most. One-hit objects, which dominate CDN traces, leave through the small queue without pushing popular objects out; a test inserts a thousand one-hit keys and checks that a frequently read key survives. And it is a few hundred lines with no frequency sketch to size and age.

The paper counts objects; cachet counts bytes. Each object is charged its body, its headers and a fixed overhead of 256 bytes, so many tiny objects still count. The ghost queue holds as many key hashes as the main queue holds objects, with a floor of 64. The paper's promotion threshold is a parameter; cachet promotes on a single read in the small queue.

The store is split into 16 shards by key hash, each with its own lock and an equal slice of the budget. An object larger than the per-object limit or than a shard is refused. Removal leaves stale queue entries behind, which eviction skips; a shard compacts its queues when stale entries outnumber live ones.

## Large objects as slices

A response over the route's `max_object_bytes` used to stream through uncached, so media and downloads never hit the cache. With `slice_bytes` set, it is cut into slices as it arrives (`slice.rs`). The default is 1 MiB, held to at most half of `max_object_bytes` so a slice with its headers is always storable, and slicing is off when that leaves less than 64 KiB. Each slice is stored as an object of its own under the URL's key plus its index. Once every slice is in, a manifest is stored under the URL itself: the response's status and headers, no body, and an internal `edgefront-slices: <slice size> <total>` field that never reaches a client. Each slice carries the object's surrogate keys plus one of its own (a hash of the URL key), so a purge by tag removes the slices with the object. `Cache::purge` adds that tag to every purge by URL.

A hit on a manifest is answered from the slices: the whole object, or a single range, with the manifest's preconditions evaluated first (`If-Match`, `If-None-Match` and the rest, as for any hit). The response body is fed slice by slice from a task, never more than a few slices in memory at a time. When a range needs slices that are no longer held, the request goes to the origin with `Range` widened to whole slices. The `206` answer is stored slice by slice, and the client gets its own range out of it. A whole-object request with a slice missing fetches the object again. Several ranges on a sliced object get the whole object with 200, which RFC 9110 permits.

**Validators.** A `206` for missing slices is checked against the manifest: the same total length and the same strong entity tag. If either differs, the object changed at the origin. The old manifest and every old slice are purged before the new slices are stored, and a new manifest is stored after them. Every slice read is checked against the manifest's strong entity tag too, so a response never mixes bytes of two versions.

**While filling.** Every client of a slice fill, the one that started it included, reads through the fill's `Progress`. Slices already stored come from the cache, and the slice still arriving is read from its own `fill::Filling`, which holds at most one slice. The flight is held open until the last slice is in, so a client that arrives during a fill of any size gets its first byte at once. A reader slower than the origin can fall behind the memory tier, which may already have evicted a slice whose disk write is still queued. So the fill also keeps its last 64 completed slices for such readers, and a reader that still misses waits for the disk queue and looks again. If the origin fails partway, or sends more or fewer bytes than it declared, every reader fails; the slices already stored stay, but no manifest is written.

`crates/edgefront-cache/tests/slices.rs` runs it over real TCP: a 5 MiB object on a route that stores at most 1 MiB, in 256 KiB slices. All 20 slices are stored, and whole, ranged, suffix and conditional requests are answered from them without the origin. Removing one slice makes a range over it fetch `bytes=1310720-1572863` and nothing else. Changing the object at the origin makes the next missing slice's fetch replace the old slices, so no old byte is served. A client joining a fill paced over 1.6 s gets its first byte within 50 ms. A purge by URL removes the slices.

`tests/e2e_large_objects.rs` runs it on the real binary, with the segment store and a 2 GiB object:

1. A whole fetch, checked byte by byte, is cut off by SIGKILL after 600 MiB, once the first slices are on disk.
2. After a restart, there is no manifest, since the fill never finished. A range at 100 MB fetches the object once and is answered as soon as its slice arrives.
3. Ranges at the start, across a slice boundary, across 3 MiB at 1 GiB, at a third and at the last byte are then hits, with every byte checked and no further origin request.
4. All 2,048 slices and the manifest reach the segment store.

It takes about a minute in a debug build.

## Surviving a restart: the disk tier

The disk tier (`store/segment.rs`) is optional and write-through: every stored entry is queued for disk, and memory holds the hot subset. A memory eviction then costs nothing, and a restarted node comes back warm instead of sending every request to the origin at once. Writes go through a bounded queue (1,024 entries by default) to one thread. When the queue is full the write is skipped and counted, because the entry is still in memory and a cache may forget.

**A log of segments.** The tier used to store one file per URL. It is now a log-structured segment store. Every write is appended to the active segment file, which is sealed at one eighth of the tier's budget (between 1 and 64 MiB), and the next one is then started. Each frame holds a magic number, a kind (put or delete), a length and a SHA-256 prefix over all of them. A put's body is the codec record from before: the key, statuses, freshness and headers for every variant, then the bodies, each with its own SHA-256. An in-memory index maps each key to the place of its newest put, and keeps the surrogate-key index. A removal or purge appends a tombstone, so a restart that replays the log does not bring the object back.

**Space, eviction and compaction.** The segments' total size is held to the tier's budget. When a write would go over it, the oldest segment is deleted with every object still in it, which is FIFO eviction a segment at a time. Replacements and deletes leave dead frames behind. When the write queue is empty, the writer thread compacts: once less than half of the oldest segment is live, it copies the live frames to the head of the log, syncs them, and deletes the segment. Compacting only the oldest segment means no older segment is left for its tombstones to guard against, so they are dropped. `cachet_disk_written_bytes_total` over `cachet_disk_user_bytes_total` is the write amplification, and `cachet_disk_compacted_bytes_total` counts compaction's share of it.

**Crashes.** Frames are appended and synced, so a crash can only tear the last frame of the active segment. At startup each segment is scanned, and it is truncated at the first frame that is short, has the wrong magic or fails its checksum. Reads check the frame checksum and the record's own checksums again, and a record that fails is dropped and treated as a miss, so a corrupt object is never served. A unit test cuts a segment at every byte offset and checks that each object read back is either whole or absent. `tests/failure.rs` kills the real binary with SIGKILL, appends half a frame to its segment, stops the origin, and restarts. The object comes back as a hit and the torn bytes are cut off.

**Warm restart from a snapshot.** A scan reads every byte of every segment. A clean shutdown avoids it by writing the index to `index.snap` (`store/index.rs`): the segments with their lengths and live bytes, then every key with its segment, offset, frame length and surrogate keys, then a SHA-256 over all of it. The next start trusts the snapshot only if its checksum holds, every length in it is in bounds, and every segment it names is still on disk and at least as long. Segments are append-only, so the bytes it describes are unchanged. It then replays only the frames written after it, and deletes the snapshot. A crash later therefore falls back to a full scan instead of trusting an index that no longer matches the log. `crates/edgefront-cache/tests/segment_restart.rs` fills the store with 1,000,000 objects, shuts it down and opens it again. In a release build on the benchmark machine (16-core arm64) the store is ready in 164 ms (the median of three runs; 159 to 166 ms), against the issue's 1 s, and the bench workflow runs the same test in release on every push. The first version took 305 ms here and 1.02 s on a 4-vCPU GitHub runner. Interning the surrogate keys while decoding, sizing the index and each surrogate key's set up front, and inserting entries without the removal check a log replay needs brought it down.

Files of the old one-file-per-URL layout are removed at startup, which empties that tier once.

## Removing content: surrogate keys and the purge log

Origins tag responses with a `Surrogate-Key` header, a space-separated list of keys (a convention several CDNs use; there is no RFC). Each memory shard and the disk tier keep an index from tag to keys, updated on insert, replace, eviction and removal. `POST /purge` on the admin listener takes `{"tags": [...], "urls": [...]}` with up to 1,000 targets and a 64 KiB body, behind a bearer token. The token is compared through SHA-256 digests with no early exit, which also hides its length.

A fetch that started before a purge can finish after it. Without care, it would put the purged response back. Each fetch records the purge log's epoch when it starts. After storing, the cache asks the log whether a purge since that epoch matches the key or any of its tags, and removes its own insert if so. A purge records itself in the log before it removes anything, so either the purge removes the insert or the check sees the purge. The log keeps the last 4,096 targets; if it no longer reaches back to a fetch's epoch the answer is a conservative yes. The disk writer applies the same check before and after each write.

## Getting a purge to every node

`cluster.rs` spreads a purge to every node. The node that accepts a purge turns it into a message with a unique id, its node id, the time, and the targets, serialises it to JSON and signs those exact bytes with HMAC-SHA256 (RFC 2104) under a key shared by the cluster. The key is never sent. A receiver checks the signature over the raw body before parsing anything, then refuses messages older than the window (600 seconds by default) or more than 60 seconds in the future, and remembers ids for the window, so a captured message cannot be replayed. A new message is applied and then relayed, as the same signed bytes, to the receiver's peers other than the origin and the sender. This is the flooding form of the epidemic broadcast in Demers et al. (1987): each node forwards a message once, ids stop loops, and a purge still reaches a node that the first node cannot reach directly. A test with three nodes in a line checks that.

Each peer has its own queue (1,024 messages) and one delivery task, so a slow or dead peer delays only its own messages. A failed delivery is retried with exponential backoff from 100 ms up to 5 seconds until the message would be too old for the peer to accept. A peer that answers with a 4xx other than 429 has refused the message (usually a different key) and is not retried. A test stops a peer, purges, starts the peer again on the same disk directory and watches the purge arrive and remove the object that came back from disk.

With N nodes a purge costs O(N²) messages. That is fine for tens of nodes and wrong for thousands, where a tree or a fan-out service would be needed.

## Tiers: owners, a shield and hot keys over SWIM

Without tiers every node fetches from the origin on its own, so ten nodes send up to ten requests for one object. With `[tier]`, nodes find each other with SWIM and spread the keys between them, so the cluster sends one.

**Membership** (`edgefront_core::cluster::swim`). Each node pings one member per protocol period (250 ms by default), the next of a round shuffled again each time it ends, so every member is pinged once a round. No ack within 30% of a period and it asks three others to ping the target for it (ping-req); no ack by the end of the period and the target is *suspect*. A suspect that does not refute within the suspicion timeout (1 s) is *dead*. A node that hears it is suspected raises its incarnation number and announces itself alive again, and the precedence rules (alive at a higher incarnation beats suspect, suspect beats alive at the same one, dead beats both, and a restart's higher incarnation beats dead) settle every disagreement the same way on every node. Changes ride on pings and acks, each sent three times the log2 of the cluster size, and a member heard from for the first time is sent the whole membership that way. Every datagram is at most 1,400 bytes and signed with HMAC-SHA256 under `CACHET_CLUSTER_SECRET`, and the tag is checked before the JSON is parsed. The protocol is a state machine over a millisecond clock, so it is tested on a simulated network: over 60 runs of ten nodes at 0, 5 and 10% loss, a killed node was dead on every other node within 2.3 s at worst, and no live node was ever declared dead. Each node announces its HTTP address and weight in its metadata.

**Owners** (`tier::owner`). A key's owner is its weighted rendezvous winner among the live edge nodes: each node scores the key `weight / -ln(h)`, `h` a hash of the key and the node in (0, 1), and the highest wins. A membership change moves only the keys of the node that came or went; with ten nodes, removing one moved 9,943 of 100,000 keys (a property test checks it for any membership and weights). The hash (FNV-1a and a SplitMix64 finaliser) is fixed in the code, not the standard library's, so different builds agree on owners. I chose rendezvous hashing over a ring with virtual nodes because it needs no table to build or keep in step, weights are a multiplication, and the runner-up for a key, where it goes if its owner leaves, falls out of the same scores.

**Peer fetch** (`tier::peer`, wired in `src/proxy.rs`). A miss on a node that does not own the key goes to the owner instead of the origin, over HTTP with the hop header `edgefront-tier: <node> owner <hmac>`. The tag covers the sending node, the tier, the method and the target, under the cluster key. The owner serves it from its cache or fetches it, and its request collapsing makes every node's misses for one key a single fetch. A node that receives a validly signed hop never sends the request to another peer, so a request makes at most one peer hop even while two nodes' views of the membership disagree. A hop header without a valid signature is removed before the cache sees the request. The node that asked passes the owner's response on without storing it (`tier::Transient`), so each object is kept once in the cluster. When the owner cannot be reached (refused, or no answer within the response timeout), the node goes to the origin itself and counts a fallback; once SWIM declares the owner dead, its keys have new owners.

**Shields** (`tier::shield`). `[[tier.shields]]` names, per host and path prefix, the nodes misses go to before the origin. The most specific route wins. Within a route's shields, each key goes to its rendezvous owner among those alive, so all of the edge's misses for one key reach one shield, which collapses them into one origin request. A shield never sends a miss to another shield, and the edge nodes' owners are chosen among the nodes that are not shields. A miss therefore takes at most edge, owner, shield, origin. With ten edges and a shield, a cold object asked of every edge at once, ten times each, reached the origin once (`tests/tier.rs`).

**Hot keys** (`tier::hot`). Each node counts its requests in a count-min sketch, 4 rows of 4,096 counters, all halved every second, so a key's count settles near twice its rate. A key whose count reaches twice `hot_rate` (50 a second by default) is hot on that node. Since every node forwards its misses for a key to the owner, the owner sees the key's whole cluster rate. Hot keys are replicated in two ways:

- The owner of a key that gets hot has its two runners-up, the next nodes in the key's rendezvous order, fetch it from the owner and keep it. The hop header's `replica` tier tells them to. That makes 3 replicas whatever traffic each node sees, and the first runner-up is the key's next owner, so it has the key if the owner leaves.
- Any other node that sees the key hot keeps the owner's response for it instead of passing it on, and serves it locally.

Together, a hot key makes no peer hop from any node that asks for it often. When a node's count for a key falls below half the threshold, the key is demoted there. The node drops its copy unless it is one of the key's 3 replicas, and the hot set per node is bounded at 1,024 keys.

`tests/tier.rs` checks both:
- With the top 100 keys requested on all ten nodes, every node promoted all 100, and a further request for each on every node made no peer hop. Once they cooled, exactly the 300 replica copies were left.
- A key asked only of its owner was pushed to its two runners-up, which fetched it from the owner, not the origin.

**Offload.** On a Zipf 1.0 trace of 40,000 requests for 1,000 keys, spread over ten nodes, ten nodes without tiers sent 6,907 requests to the origin (82.7% offload). Ten tiered nodes sent 1,000, one per key (97.5%), the same as one node that saw every request.

What it does not do: a node's keys move to their runner-up only once SWIM declares it dead, about 1 to 2 s, and until then its misses go to the origin. The hop header's signature can be replayed for the same method and target, which can only make a node skip the peer step. Cluster traffic is plain HTTP and signed UDP, not encrypted. Every node must have the same `[[tier.shields]]`, since that list decides which members are edges.

## Choosing an origin

`origin.rs` keeps an ordered list of origins. Requests go to the first healthy one. Requests without a body move to the next origin on a connection error, a timeout before response headers, or a broken response. A broken response on a pooled connection is retried once on the same origin first, since that is how a connection the origin already closed fails. If every origin is marked down, they are still tried in order: health data lags behind recovery, and failing closed would turn a brief blip into a full outage.

Health comes from active probes (`GET /healthz` every 2 seconds by default) and from connection failures and timeouts in real traffic, which share the same counters. An origin is marked down after three consecutive failures and back up after two consecutive successes. A broken response does not count against health.

## Input limits and secrets

Both of a node's listeners are edgefront-core's `listener`, the one the proxy track serves on. Clients get 10 seconds (`timeouts.client_header_ms`) to send a request head, timed from the accept for the first request and from its first byte for later ones; the head may be at most 64 KiB and 100 fields, and a larger one gets 431. A keep-alive connection may then sit silent for `timeouts.idle_ms`, which defaults to the header timeout because cachet's own accept loop closed silent connections after that long. A request counts as open until its response is fully written, so neither timer cuts a slow origin or a long download. Request targets over 8 KiB get 414. Request bodies over 10 MiB get 413, checked against Content-Length before reading and enforced while streaming otherwise. A request whose `Via` names this node gets 508. Origin bodies are buffered only up to the per-object limit (8 MiB); the declared length is checked before reading, and a body that turns out larger streams through to the one client that asked, uncached, without buffering the rest. Only the first 64 surrogate keys of a response are kept, keys over 128 bytes are dropped, and a URL keeps at most eight Vary variants, so an origin varying on something like User-Agent cannot fill the cache with one URL.

The admin listener binds to localhost by default. Without `CACHET_ADMIN_TOKEN` the purge API is off. Without `CACHET_CLUSTER_SECRET` (at least 32 bytes) the peer endpoint is off, and a config with peers refuses to start. Secrets come only from the environment and are redacted from `Debug` output.

## What happens when things fail

| Situation | What happens |
|---|---|
| Origin refuses connections | Next origin is tried; after three failures it is marked down and skipped. Stale copies inside `stale-if-error` are served; otherwise 502. |
| Origin hangs | 504 after the response timeout (10 s), or the next origin. A stalled body while caching is a timeout after 30 s. |
| Origin returns 5xx | Passed on, or the stale copy inside `stale-if-error`. |
| Origin sends malformed HTTP | 502, never stored. |
| Popular object expires | One origin request; every concurrent client waits for it. |
| Client disconnects mid-fetch | The fetch continues for other waiters and the cache. |
| Node crashes | Disk records are whole or absent. Restart deletes temporary files and corrupt records, and serves from disk. |
| Disk write queue full or disk fails | Write skipped and counted; memory still serves. |
| Peer unreachable during a purge | Retried with backoff for the message window, then dropped and counted. |
| Peer down for longer than the window | It misses the purge. Objects it still holds expire normally. |
| Forged, replayed or stale purge message | Refused before or after parsing, counted. |
| Purge races a fetch | The fetched response is not kept. |
| A tier node dies | Misses for its keys go to the origin (a fallback) until SWIM declares it dead, about 1 to 2 s; then its keys belong to their runners-up. |
| A forged hop header | Removed before the cache sees the request. |
| Shutdown | Stops accepting and closes idle connections at once. Open requests get up to 10 s (`shutdown_ms`) to finish, each answered with `Connection: close`; connections still open after that are closed. Then the disk queue is flushed. Queued purge deliveries are lost. |

## Compressed variants, shared dictionaries and Early Hints

**Which coding.** `encoding.rs` reduces Accept-Encoding to the one coding a response will use, among identity, gzip, br and zstd: q weights, `*`, an excluded identity, ties to the server's order (br, zstd, gzip, identity). A variant stored by a compressing route carries a stored-only `edgefront-variant` field (`source`, or the coding it was compressed into), which the disk format keeps and no client sees. `Entry::find` leaves Accept-Encoding out of such variants' Vary match and picks among the codings held with `encoding::negotiate`, so one URL has at most four, and a collapsed follower is matched the same way. Routes that do not compress match Accept-Encoding raw, as cachet 0.1 did, which keeps `make difftest-cache` unchanged.

**Compressing on fill** (`variants.rs`). A source is a `200` with a text-like type, at least `min_bytes`, no content coding, no `Content-Range` and no `no-transform`. It gets `Vary: Accept-Encoding` before it is stored, and is then compressed on tokio's blocking pool, so a fill never waits, into br (quality 5), zstd (3) and gzip (6). A coding is kept only when its output is smaller than the source. Each is its own variant in the same entry as the source, with `Content-Encoding`, its own length and a weak entity tag (`"v1"` becomes `W/"v1"`, since it is another representation). Being in one entry, the variants are evicted and purged together. A newer response from upstream drops the ones compressed from the copy it replaces, `Cache::store_derived` refuses variants of a source no longer held, and compressed variants do not count against `max_variants`. A stale compressed variant is never revalidated on its own: the request goes upstream with its source's validators, and the refreshed source is compressed again.

**The budget.** `queue_limit` caps the jobs queued or running on the blocking pool, compression on fill and dictionary compression together. Past it a job is skipped and counted, and the response is served as stored. `CompressionStats` counts, per coding, jobs, bytes in and out, the time spent compressing on blocking threads (the work keeps them busy, so it stands for CPU; there is no thread CPU clock without `unsafe`), and a ratio histogram, all on `/metrics`.

**Shared dictionaries** (`dictionary.rs`, RFC 9842). A stored identity `200` with `Use-As-Dictionary` is kept under the SHA-256 of its body, with its pattern resolved against its URL, its `match-dest` and `id`. It is kept while fresh and at most `dictionary_max_ttl_secs`, within `dictionary_max_bytes` each and 64 MiB in all; past that, the soonest to expire goes. A fresh hit uses one when the request:

- names its hash in `Available-Dictionary`;
- accepts `dcb` or `dcz`;
- is for its host and pattern;
- has a `Sec-Fetch-Dest` among `match-dest`, when that is set;
- echoes its `Dictionary-ID`, if it sends one.

dcb is brotli with the dictionary as a raw prefix, and dcz is zstd with it as raw content and a window that reaches over it. Both start with their magic and the dictionary's hash, and the response varies on `accept-encoding, available-dictionary`. The compressed body is kept per URL, dictionary and coding, tied to the stored copy it came from (64 MiB, oldest out). Patterns are a subset of URL Pattern: paths, relative paths and same-origin URLs with `*` and `\` escapes. Groups, named parameters, regular expressions and search parts are not used, nor dictionary types other than `raw`. Conditional and range requests, and misses, get the usual coding.

**Early Hints** (`early_hints.rs`, RFC 8297). A stored HTML page's hints are its `preload`, `modulepreload` and `preconnect` `Link` values, at most 32. When such a page must go upstream, the hints are sent as a `103` first, and the final response keeps its `Link` fields. hyper's HTTP/1.1 server cannot send a 1xx: it refuses one from a service, and its only informational support is the client's `on_informational`. So `edgefront_core::interim` puts an `Interim` in each HTTP/1.1 request's extensions (not HTTP/1.0's, which RFC 9110 section 15.2 forbids), and the listener's connection stream writes what it queues ahead of hyper's next write or flush. This is safe because hyper writes nothing on a connection between reading a request and the response being returned, and does not read the next request until the response is written. Once hyper starts the final response, that request's `Interim` refuses more (16 KiB at most). Filters reach it through `RequestHead::extensions`. HTTP/2 clients get no hints, because hyper's HTTP/2 server does not expose h2's `send_informational`.

## What it does not do well

HTTP/1.1 only, plain HTTP to origins and peers; 103 Early Hints only to HTTP/1.1 clients. Peer messages are signed, not encrypted; purge targets are not secret, but deployments that care should put the admin listener on a private network.

Objects are kept whole in memory up to the per-object limit; a fill over 64 KiB with a declared length streams to its clients while it arrives, but a body without a `Content-Length` is still read whole before anyone sees it. Responses over the per-object limit stream through uncached.

Two concurrent stores of different variants of one URL can race, and one of them may be lost. The next request for it fetches again.

Conditional requests are evaluated against the stored copy in RFC 9110 section 13.2.2's order. First comes `If-Match`, with the strong comparison, so a weak stored tag never matches. Then `If-Unmodified-Since`, which is ignored beside `If-Match`, when its value is not exactly one HTTP date, or when the copy has no `Last-Modified`. Either failing gives 412. Next come `If-None-Match`, or `If-Modified-Since` without it, which give 304. Then `If-Range` and `Range`. The cache answers these from what it holds; a copy that has gone stale on the origin can still pass a precondition until it is revalidated, as with any cached answer.

Age depends on the origin's `Date`, so clock skew between origin and cache shifts apparent age, as the RFC acknowledges. A `Date` in the future counts as zero apparent age.

Without a snapshot (after a crash), the startup scan reads every segment in full, which takes time proportional to the bytes on disk.

## The benchmark harness

Every track measures with `crates/edgefront-bench`, so that a number from one track can be read next to a number from another. A run is one scenario (`bench/scenarios/`) against one target (`bench/targets/`), and gives one result file.

**Open loop, timed to the microsecond.** `edgefront_bench::load` sends request `k` of a phase at `k / rate` seconds after the phase starts, whatever earlier requests did, and measures each response from that due time, so a stall shows in every request it delays. The due time only means something if requests leave on it. tokio's timer fires up to a millisecond late, so a dispatcher that slept until each due time added about a millisecond to every response time: the first container runs measured a 1.4 ms p50 for hits whose service time was 66 µs. The dispatcher now sleeps until 2 ms before a due time and yields through the rest, which also lets its thread run the worker it has just woken; the same runs then measured a p50 of 54 µs against a service time of 53 µs. The service time from the moment each request was written is kept beside the response time, so a gap between them is visible in every result.

**One origin for every target.** `edgefront_bench::origin` serves `GET /obj/<size>/<name>` with `Cache-Control: public, max-age=3600`, a strong `ETag`, a fixed `Last-Modified` and `Content-Length`, the body streamed in 1 MiB frames cut from one shared buffer. It counts the object requests it answers; the load generator reads the count before and after the measured phase, and `1 - origin requests / completed requests` is the hit ratio a result reports. That is measured at the origin, not taken from a target's headers, so every product is judged the same way.

**Containers on one private network.** `Runner::run` creates a network, starts the origin, the target's sidecars and the target, and then the load generator as a container of its own (`edgefront-bench load`), each pinned to a CPU set: on 16 CPUs the target gets 0-3, the origin 4-9 and the load generator 10-15 (`--target-cpus` changes the first). The load never crosses the host's port forwarding, which on Docker Desktop costs more than the caches being measured. Config files are rendered from `{{...}}` templates (the origin's address, the CPU count, the cache size, the largest object) and copied in before each container starts, so every target gets the same cache size, worker count and origin; `bench/targets/README.md` lists what each product is given and every departure from its defaults. Each container and the network are removed afterwards, whether the run worked or not, and a failed run reports the target's last log lines. Only one run uses a container runtime at a time: each takes a lock, the container `edgefront-bench-lock`, which only one process can create, and images built from the repository are tagged per checkout (`local-<hash of its path>`), so two checkouts sharing a machine wait for each other instead of sharing its CPUs and swapping each other's images.

**Resources from the cgroup.** The load generator runs with `--cgroupns=host` and reads the target's cgroup v2 files, under `docker/<id>` (cgroupfs, Docker Desktop) or `system.slice/docker-<id>.scope` (systemd, most Linux hosts). Peak RSS is the highest `anon + file_mapped` from `memory.stat`, summed over the target's containers and sampled every 100 ms; peak memory is the sum of `memory.peak`, which also charges page cache and tmpfs, so a target that caches on a tmpfs pays for it there. CPU seconds are `usage_usec` from `cpu.stat` over the measured phase. The run also reads `cpuset.cpus.effective` and refuses a result whose target was not on the CPUs it was pinned to. Containers are pinned with `--cpuset-cpus`, which sets the same kernel affinity mask `taskset -c` does for a process (`CpuSet::taskset` builds that command for targets run outside a container). Image sizes come from `docker image inspect`.

**A result is checked before it is written.** `edgefront_bench::report::BenchResult` is the JSON a run writes to `<out>/<scenario>/<target>.json`, and `bench/schema/result.schema.json` (JSON Schema 2020-12) fixes its fields: the scenario as run, the target and its images, the machine and CPU sets, the measured phases (throughput, p50 to p99.9 and the maximum of response and service time, status classes, errors by kind, body bytes, origin requests and hit ratio), each phase in brief, and the resources. `extra` holds a track's own numbers by name. The harness validates every result against the schema before writing it, with `edgefront_bench::schema`, a validator for the keywords the schema uses that refuses a schema using any other, and CI checks the written results again with `check-jsonschema`, a complete validator. `report::render` turns a directory of results into Markdown: a section per track, a table per scenario, a row per target, the machine, and the command that reproduces it.

**HTTP/2, gRPC and open streams.** The origin speaks HTTP/1.1 and prior-knowledge HTTP/2 on one port: it reads a connection's first four bytes, and `PRI ` (which starts the HTTP/2 preface and no HTTP/1.1 method) makes it HTTP/2, with room for 10,000 streams a connection; the bytes read are handed back to the protocol (`Prefixed`), so nothing is peeked twice and a client that sends half a preface and closes is simply dropped. It answers a unary gRPC call to `/edgefront.bench.Objects/Get`, whose one message is an object path, with that object as one message and `grpc-status: 0` in the trailers, so a gRPC scenario draws its objects exactly as a GET scenario does. `origin_delay` holds each object request, GET or gRPC, before it is answered (`edgefront-bench origin --delay`), which is how a scenario sets the streams a run keeps open. Over HTTP/2 the load generator's in-flight count is concurrent streams, from the moment a request is written to the end of its response. A file may hold several scenarios over shared defaults (`[[scenarios]]`); the runner copies the whole file into the load generator's container and names the one to run (`load --name`).

**The harness tests itself.** `crates/edgefront-bench/tests/harness.rs` runs the load generator's side of a container run in process. A target that holds every response for 100 ms, one second into a 2 s measured phase at 500 requests per second over two connections, gives a response-time p99 of 80 ms or more while the service time stays lower. Two runs of 8 s at 1,000 requests per second against a target that answers in 100 ms, on a runtime of its own, agree within 5% on throughput and p99. The repeated container runs of `cache-hit` are in the results below.

`examples/bench.sh` runs `cache-hit` against edgefront and Varnish and prints the report; on this Mac (16-core arm64, Docker 28, 16 CPUs and 7.7 GiB for its Linux VM) it takes 143 s with the images already built. Both answered all 300,000 measured requests at 98.0% hits, the scenario's target:

| edgefront | 5,000 req/s | 46 µs | 124 µs | 196 µs | 82.9 MiB | 11.0 s | 12.7 MiB |

### The regression gate

A pull request that touches the crates runs `bench/ci/gate.toml`, 2,000 requests per second of 1 and 4 KiB hits for 20 s after 2 s of warm-up, against edgefront on one CPU of a GitHub-hosted runner. It does this ten times for the candidate and ten times for the commit the change is based on (the pull request's base, or for a manual run the branch's merge base with main), alternating them on the same runner with the first side swapping every round; the job takes about ten minutes. Judging against the change's own base, rather than a fixed commit, means a pull request answers for its own diff and not for everything merged since the gate was set. `edgefront_bench::gate` judges two metrics: response-time p99, and completed requests per CPU second of the target. An open-loop run's own throughput is its schedule, so the throughput a CPU buys is the throughput that falls when the hit path slows down.

A metric fails only when two things hold. A one-sided Mann-Whitney U test must say the candidate is worse at p < 0.01; with ten samples against ten, that takes at least 81 of the 100 candidate-baseline pairs, so up to 19 may go the wrong way. The worse median must also exceed the 5% tolerance. The test is exact while there are at most 250,000 orderings, with ties given midranks, and uses the normal approximation with tie and continuity corrections beyond that. The binary and the image have fixed ceilings, about 10% above their sizes when the gate was set. The verdict is JSON naming each metric with its medians, change, p-value and tolerance, and the job summary shows it as a table.

The gate first compared pull requests against committed samples, as cheaper runs. The runners' noise ruled that out, measured as follows (`bench/gates.toml` has the numbers):

- Hosted runners come on several CPU models, and one build measures up to 60% apart between them, so samples have to be kept per model (`bench/baseline/gate.json`).
- Within one model, 18 recording runs on unchanged code moved their medians by up to 27% at p99 and 18.5% in requests per CPU second on the EPYC 9V74. Even the EPYC 7763, the steadiest model, failed an unchanged run against its committed samples at p99 +6.8%.
- Alternating the baseline commit with the candidate on the same runner removes the runner from the comparison. Ten unchanged runs that way across five CPU models all passed. None was significant at 0.01 on either metric. The largest median difference was 7.6% (better) in requests per CPU second, and 4.0% at p99.

`committed_models` therefore lists no model, and every pull request is compared on its own runner. The proof is a branch that spins 3 µs in every hit, which costs 8 to 34% of requests per CPU second depending on the CPU. With 20 s runs it failed the gate twice in three tries: +11.8% on a 9V74 and +7.9% on a 7763, both at p = 0.004. The third try, on a 7763, was 8.6% worse at p = 0.016, short of significance. Over every try of that branch, with both run lengths and both designs, the two slowdowns measured above 14% (16.1% and 33.6%) failed. Between 7.9% and 13.6%, three of five failed, and slowdowns measured at 4.3% and 6.6% (8 s runs) passed. With five runs a side a 10% slowdown therefore failed the gate most of the time but not every time: at p < 0.01 the exact test needed 24 of 25 pairs worse, and one run spoiled by a noisy neighbour was enough to miss. So the gate went to nine runs a side, as the proxy's p99 gate had, which tolerates 14 spoiled pairs of 81 at the same level and the same 5% tolerance. A push to a branch named `bench-gate-*` runs only the gate job, against the branch's merge base with main, which is how a planted slowdown or an unchanged branch is put through the gate without a pull request.

## Why these dependencies

tokio, hyper and hyper-util provide the runtime, HTTP/1.1 server and pooled client; http, http-body-util and bytes are their shared types. httpdate parses the three HTTP date formats. sha2 and hmac provide the record checksums and message signatures; writing either by hand would be a mistake. serde, serde_json and toml read the config and the purge and peer messages. tracing and tracing-subscriber give JSON logs. rustls terminates TLS, with ring as its crypto provider rather than its default aws-lc-rs, which needs a C toolchain and CMake to build and brings FIPS support nothing here needs; tokio-rustls is the small adapter that runs rustls over tokio streams, from the same maintainers. They take the budget to 16, and ring itself to 17: the OCSP signature checks and SHA-1 `CertID`s, and the ACME account keys and signatures, need ring's primitives, which rustls uses but does not expose. criterion is a dev-dependency for benchmarks. hyper's `http2` feature is on for the whole workspace since the edge listener serves HTTP/2 (#92), and h2 itself is the 18th: the upstream pool reads h2's own error to tell a stream the origin refused unprocessed (a GOAWAY that excluded it, or `REFUSED_STREAM`), which is safe to send again whatever its method, from one that may have been acted on, and hyper's error does not say which. Its latency histogram is written here instead of taken from the hdrhistogram crate, which the harness's plan named, because the workspace is at its direct dependency budget and the harness needs only recording, merging and quantiles; its tests hold every quantile to three significant digits against the exact value. For the same reason the harness checks results against their JSON Schema with a small validator of its own, which refuses any keyword it does not implement, and CI checks them again with the complete `check-jsonschema`; container runtimes are driven through the `docker` command line rather than an API client. Metrics, the Prometheus text format, request ids, the disk record format, request collapsing and the S3-FIFO store are written here because each is small.

Direct dependencies are pinned to exact versions published at least two weeks before they were added, and the lockfiles pin transitive crates to releases at least as old. One exception: cargo audit reported RUSTSEC-2026-0385 against ctutils 0.4.3, a transitive dependency of sha2 and hmac, so both lockfiles use ctutils 0.4.4, the first fixed release, published four days before it was taken.
