# Changelog

Changes to edgefront, newest first. Each week's entries name the roadmap issue they close or advance.

## Unreleased

### Cache

- `edgefront_cache::encoding` reads Accept-Encoding (RFC 9110 section 12.5.3) and maps each request to exactly one of identity, gzip, br and zstd, so a URL has at most four encoded variants however clients spell the header. It handles q weights, `*`, an excluded `identity`, `x-gzip`, case, several field lines and malformed members (skipped, never the whole field). Ties go br, zstd, gzip, identity. The new `accept_encoding` fuzz target runs in CI with the others. (#96)
- Hot keys are replicated to 3 nodes. When a key gets hot on its owner, the owner has the key's two runners-up in rendezvous order fetch it and keep it (the hop header's `replica` tier). Every other node that sees it hot still keeps its own copy. On demotion a node drops its copy unless it is one of the 3 replicas. `cachet_tier_replicas_sent_total` counts the pushes. (#93)
- `examples/tiered.sh` starts five edge nodes and a shield of the release binary and prints the origin's request counts: 20 concurrent requests for one cold URL over the five edges make one origin request, and 1,000 requests for 200 objects make 200. An edge killed with SIGKILL is noticed by every node in about 1.6 s, and its keys come back from the shield without another origin request. CI runs it. The README and docs/DESIGN.md ("Tiers: owners, a shield and hot keys over SWIM") describe the tiers. (#93)
- `tests/tier.rs` runs ten edge nodes and a shield in one process over loopback, each a whole node with its own listeners and SWIM socket. A cold object asked of every edge at once, ten times each, reaches the origin once. A node killed without leaving is gone from every view in 1.5 to 2.0 s, and only its own 986 of 10,000 keys move. A Zipf 1.0 trace of 40,000 requests over ten nodes offloads 97.5% (82.7% for ten separate nodes). After a warm-up that makes them hot however slow the machine (two requests back to back, `hot_rate = 1`), the top 100 keys make no peer hops on any node, and their copies on non-owners are dropped once they cool. A dead owner's key is fetched from the origin until SWIM notices, and a forged hop header is ignored. (#93)
- `[tier]` puts a node in a cluster of caches. Members find each other with SWIM, and a miss on a node that does not own the key goes to its owner (`tier::peer`), signed with a hop header so it makes at most one peer hop, and the owner's response is passed on without being stored. `[[tier.shields]]` names per host and path prefix the shield nodes the owners' misses go to, and a shield collapses them into one origin request (`tier::shield`). A count-min sketch per node (`tier::hot`) finds keys requested over `hot_rate` a second, which that node then keeps itself until they cool. When an owner cannot be reached, the miss goes to the origin. `/metrics` has `cachet_tier_*` counters. (#93)
- `edgefront_cache::tier::owner` decides which node owns a cache key by weighted rendezvous hashing, with a hash fixed in the code so every build in a cluster agrees. A node's share is its weight over the total, and a membership change moves only the changed node's keys: with ten nodes, removing one moved 9,943 of 100,000 keys, all of them its own. A property test checks that for any membership and weights. (#93)
- `edgefront_core::cluster::swim` is SWIM membership for the cache's tiers and the limiter's cluster: a ping each protocol period to the next member of a shuffled round, ping-req through three others when it goes unanswered, suspicion with incarnation numbers and refutation, changes piggybacked on pings and acks a bounded number of times, and every datagram signed with HMAC-SHA256 and checked before it is parsed. The protocol is a state machine over a millisecond clock, tested over a simulated network: ten nodes join through one seed, and a killed node is dead on every other node within 2.3 s over 60 runs at 0 to 10% loss, with no live node ever declared dead. (#93)
- The `conformance` workflow runs the open http-cache-tests suite (github.com/http-tests/cache-tests, pinned to commit 3942fbf) against the binary as a shared cache, on GitHub's runner only (`tests/conformance.rs`). Each result is classified by the suite's own rules, and the run must match `tests/conformance/allowlist.toml`, which lists every required or optimal test that does not pass with its reason; a result that changes either way fails the job. 177 of 179 required and 137 of 151 optimal tests pass. The raw results, the classification, a summary and the binary's log are uploaded as the `http-cache-tests` artifact. (#90)
- The benchmark gate runs ten alternating runs a side, the owner's choice of 10+10 runs. At p < 0.01 a metric then needs 81 of the 100 candidate-baseline pairs worse. Proved on hosted runners: a planted slowdown sized as a share of the process's own CPU per hit failed six runs of six, 7.6 to 15.7% worse in requests per CPU second at p of 0.0002 or less, and six unchanged branches passed both metrics. The job takes about 10.5 minutes. (#87)
- A request body of up to 64 KiB on an idempotent request (PUT, DELETE, OPTIONS, or a GET with a body) is read whole before it goes to the origin, so when the pooled connection it was sent on turns out closed (an origin's keep-alive timeout ending it as it is reused) it is sent again on a fresh one, as bodiless requests already were; it also fails over to the next origin whole. Larger and POST bodies still stream and are sent once. The http-cache-tests suite hit this as an intermittent 502 on its `PUT /config` requests against Node's 5 s keep-alive. (#90)
- Fixes the http-cache-tests suite found. `CDN-Cache-Control` (RFC 9213) now replaces `Cache-Control` and `Expires` for the cache's own decisions when it parses as a Structured Fields dictionary. Any final status from 200 to 599 but 206 and 304 is stored when it has explicit freshness, or heuristic freshness with `public`; a 5xx stored this way never replaces a good copy that `stale-if-error` could serve. An `Age` list is read by its first member. Overflowing delta-seconds clamp to 2^32 - 1 rather than 2^31. Dates parse with names in any case, and an rfc850 two-digit year is the nearest one at most 50 years ahead. `If-Modified-Since` on a hit without `Last-Modified` is judged against the stored `Date` (RFC 9111 section 4.3.2), so `make difftest-cache` sends it only where the origin sends `Last-Modified`. (#90)

- `tests/e2e_large_objects.rs` caches a 2 GiB object as 2,048 slices on the segment store. It kills the node with SIGKILL after 600 MiB of the fill, restarts it, and serves ranges across the object, every byte checked. A slice fill now keeps its last 64 slices for readers that fall behind the memory tier, and a reader that still misses waits for the disk queue, so a slow client is not cut off while the slice's disk write is queued. (#90)
- Large objects are cached as slices (`edgefront_cache::slice`, `slice_bytes`, 1 MiB by default and at most half of `max_object_bytes`). A response over the object limit is cut into slices as it arrives, each stored under its own key, followed by a manifest under the URL. Hits are served whole or by range from the slices, and missing slices are fetched with `Range` widened to whole slices. A 206 whose strong entity tag or length differs from the manifest's replaces the old slices, and every slice read is checked against the manifest's tag. A purge by URL or tag removes the slices. Clients joining a slice fill read the stored slices and the one arriving, with at most one slice held in memory per fill. Such responses used to stream through uncached; `slice_bytes = 0` keeps that behaviour. (#90)
- Streaming fill. A storable response that declares a length over 64 KiB is streamed to its client while it arrives, and to every collapsed client through a shared growing body (`edgefront_cache::fill::Filling`). The flight stays open until the body is in (`Lead::publish_held`), so late arrivals join. A client that arrived mid-fill got its first byte within 50 ms of the origin's first byte. An origin that fails partway, sends a body of the wrong length or times out aborts every reader, and nothing is stored. Followers with conditionals or a range wait for the whole object. (#90)
- The disk tier is a log-structured segment store (`edgefront_cache::store::segment`) in place of one file per URL. Records are appended to segment files with a checksummed frame, removals and purges append tombstones, and the segments' total is held to the budget by deleting the oldest segment. When the write queue is empty, the oldest segment is compacted once less than half of it is live. New metrics: `cachet_disk_segment_bytes`, `cachet_disk_segments`, and the write amplification as `cachet_disk_written_bytes_total` over `cachet_disk_user_bytes_total`, with `cachet_disk_compacted_bytes_total`. A torn last frame is cut off at startup, and every read re-checks its checksums. Files of the old layout are removed, which empties that tier once. (#90)
- A clean shutdown writes the index to `index.snap` (`edgefront_cache::store::index`). The next start checks it against the segments and replays only what came after. One million objects were ready in 164 ms in a release build on a 16-core arm64 Mac, and the bench workflow holds that test to under 1 s. After a crash, the snapshot is gone and the store scans. (#90)
- Hits and fills answer up to 16 byte ranges. Overlapping or nearly adjacent ranges are coalesced. One remaining range is a plain 206, several are `multipart/byteranges`, and unsatisfiable members are dropped. More than 16 ranges, or ranges adding up to more than twice the object before coalescing, get the whole object with 200. `If-Match` (strong comparison) and `If-Unmodified-Since` are now evaluated on hits and give 412, in RFC 9110 section 13.2.2's order before `If-None-Match`, `If-Modified-Since` and `Range`. The `range` fuzz target checks the new invariants. `make difftest-cache` no longer sends multiple ranges, since cachet 0.1 answered them with 200 and this is a deliberate difference. (#90)

- `edgefront_bench::scenario` reads benchmark scenarios from TOML. A scenario sets the warm-up and a constant or stepped load, the protocol, connections and timeout, the popular objects (count and Zipf exponent), a weighted object size mix and a hit ratio target. Requests are `GET /obj/<size>/<name>`, and each one depends only on the seed and its sequence number. Warm-up asks only for popular objects. After warm-up, a solved share of requests goes to objects asked for once, so the expected hit ratio meets the target against a cache that keeps everything. The expectation comes from a closed form over the Zipf probabilities and matches a replay to within a percentage point. A target the popular objects cannot reach is refused, as are unknown fields and out-of-range values. `Scenario::working_set` gives the bytes a target needs to hold them. ### Proxy

- `crates/edgefront-proxy/benches/discovery.rs` (`cargo bench -p edgefront-proxy --bench discovery`) runs discovery end to end through a running proxy: a delta feed over HTTP/2 gives one round-robin cluster 100,000 endpoints, then 1,000 changes a second for 10 s, and it reports how long the first set took to reach the balancer, each change's time from being published to the balancer using it, and resident memory. `Proxy::discovery_version` exposes the merged version a cluster balances on, so the bench can see each change land. The merger now settles only the addresses an update touches, rather than re-merging the whole set: before that, a 10,000-endpoint cluster fell 5 s behind at 1,000 changes a second. On this Mac (16-core arm64), three runs: the first set in 780 to 782 ms; change to balancer p50 23.0 to 23.5 ms and p99 31.4 to 33.3 ms (max 34 to 39 ms); RSS 298 MiB with the set, growing 34 to 36 MiB over the 10,000 changes. The roadmap's p99 under 5 ms is not met: each batch still rebuilds the cluster's endpoint list and balancer in O(n). At 10,000 endpoints the p99 is 3.8 ms. (#95)
- `edgefront_proxy::discovery::delta` is a versioned delta feed of endpoints over HTTP/2 with resume tokens. A control plane publishes to a `Feed` (upsert, remove, or set, which is diffed into changes), whose version rises by one per change, and which keeps its latest changes (`keep`). `delta::serve` streams it to HTTP/2 clients (cleartext, prior knowledge) as NDJSON lines: a `snapshot` (or `resume`) first, then `upsert` and `remove` lines with versions rising by exactly one, and a `heartbeat` when quiet. `DeltaSource` follows it with `?since=<feed id>.<version>`. The feed id is random per feed, so a restarted control plane that lost its history sends a snapshot, as it does for a token from the future or older than what it keeps. Snapshots become whole sets and changes become upserts and removals, so the merger applies deltas without full reloads. A break (the stream ends, a connect fails, three heartbeats of silence) is a failure (the last good set stays), retried from 100 ms doubling to 10 s. A skipped or repeated version, or a line that fails to parse or its checks, also drops the token, so the next stream starts with a snapshot. Lines are capped at 64 MiB. Over https (`ca_file` required, `h2` over ALPN) a `token_file` is sent as a bearer token, and never over http. Clusters take it as `{"delta": {"url": "http://feed:9000/v1/clusters/api"}}`. `tests/discovery_delta.rs` kills the feed while 900 changes stream, restarts it on the same port, and checks the client resumed from its token (one snapshot in all, the rest resumes) and ends with the feed's exact set, with every version in order. It does the same with a feed that lost its history and with a client that fell behind what the feed keeps, each getting a snapshot. (#95)

- Clusters discover their endpoints. A cluster's `discovery` block lists sources in order, each an object with one key (`{"dns": "api.internal:8080"}`, `{"srv": "_http._tcp.api.internal"}` or `{"file": "/etc/edgefront/api.json"}`, at most 16, none twice), plus `dns_servers` for the DNS ones. A rebuilt cluster balances over the ready endpoints. Endpoints that stay keep their state and their attempt series, and the series of removed ones are dropped, so churn does not grow `/metrics`. The pool, in-flight count and retry budget carry on, and the health checker and outlier detector follow the new endpoints without restarting: an endpoint that stays keeps its probe schedule, and a new one is probed at once. A cluster with no ready endpoints answers 503, no healthy upstream. A set over 200,000 endpoints, or one the balancer cannot take (Maglev's table holds 65,536), is refused and the last set kept. A reload that keeps a cluster's sources and listed endpoints keeps its discovery running. - Adaptive HTTP/2 flow-control windows (`edgefront_core::h2::flow`). A window caps the data in flight, so one stream carries at most window over round trip: the protocol's 64 KiB over 100 ms is 655 KB/s whatever the link. The upstream pool now speaks h2 directly rather than through hyper, so it owns its windows. It starts from its configured ones (1 MiB a stream, 4 MiB the connection) and, with `adaptive_window`, grows them to the measured bandwidth-delay product (`flow::Bdp`). On response data with no measurement running it sends a `PING`, counts the bytes read until the `ACK`, and when they reach two thirds of the stream window, sets it to twice what it saw (at least double), up to 16 MiB, by `SETTINGS` and `WINDOW_UPDATE`. Bytes count as the reader takes them, so a slow client never grows the windows. Cluster pools use it; the listener takes `http2.adaptive_window` (off by default) and gets hyper's version of the estimator, which starts at 64 KiB. In `tests/h2_flow.rs`, a 100 MB download through the pool over a simulated 25 MB/s link with 50 ms each way (100 ms round trip, a 2.5 MB BDP) ran at 22.6 MB/s against plain TCP's 24.4 MB/s over the same link, 92.6%. hyper's estimator, which the pool used before, reached 81.3% on the same link. - `edgefront_core::h2::Pool` is the upstream HTTP/2 connection pool. - The keyed `Table` has no 4.5-year horizon any more either.
